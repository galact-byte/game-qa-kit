# Bakin 状态过期：是否值得改变实时状态传输

当前结论：共享内存迁移已实施并通过离线及有限实机验证，按阶段成果收口；完整玩法未验收，不追加游戏或 WPR 批次。下方研究过程保留为历史依据，实际结果见末节。

## 哪段依赖可以移除

[桥的状态发布](../plugins/bakin/RuntimeBridge.cs)先在锁内给快照打时间戳，再在锁外写目标 JSON；发布线程在发布返回后才更新 `lastStatusIo`，游戏端守卫检查它。[宿主](../plugins/bakin/target.py)读完快照才计算年龄。故游戏端 `status_publish` 超时与宿主读到 1,359 ms 的状态不是同一测量，不能并为同一根因。只换宿主读取方法、延后快照时间戳或重新读取旧状态，都不能同时解决这两端的问题。

[Wolf 的既有方案](../plugins/wolf/README.md)把实时状态与文件证据分开。[Microsoft .NET 文档](https://learn.microsoft.com/en-us/dotnet/standard/io/memory-mapped-files)与 [Win32 文档](https://learn.microsoft.com/en-us/windows/win32/memory/creating-named-shared-memory)确认可在进程之间共享不关联普通磁盘文件的映射。候选改动只涉及最新状态：宿主与桥以同一份完整提交的快照为准，保留原始生成时间，游戏端用成功提交实时快照衡量发布进度，而非用线程心跳代替。证据写盘不得阻塞该发布线程；必需的回执、截图及其失败规则仍独立保留。命令、租约、按键释放、超时均不改；不得放宽写入守卫或对象权限。Wolf 的可用性不证明 Bakin 环境允许同一对象，也不证明两个历史故障由文件引起。

## 为什么不直接迁移

`continuous-11` 的 1,359 ms 是宿主观察年龄，不是写入耗时。既有 CLR 离线对照：当前文件替换与原子重命名的最大状态年龄分别为 63 ms、47 ms，都没复现。`continuous-12-system-01` 到达标题，但 ETL 没有保留目标启动窗口，且未进加载。[Windows 调度文档](https://learn.microsoft.com/en-us/windows/win32/procthread/scheduling-priorities)说明就绪线程按优先级和时间片运行；更改数据传输并不能为宿主或发布线程预留运行时间。共享内存也不能修复游戏实际卡住、快照生成失败、命令或租约路径阻塞。

## 投入上限

仅在 Bakin 再成优先项时做一次自写样本 A/B，不启动商业副本：让同一快照生产者持续生成新状态，单独延迟旧状态文件发布超过 1 秒；旧路应停，新路应仍收到真正的新快照。再让生产者停止生成快照，两条路均须在原期限判过期并保持无输入。若现有守卫不允许、两路无区分、或新路掩盖真实过期，则停止，不迁移。通过也只证明隔离了状态文件延迟；商业加载和玩法仍须另行实测。

## 实施与实机结果（后续补充）

经用户批准，已按上述思路实现 `bridge_version=3` 与 `control_transport=bakin-shm-v1`（4×64 KiB 分页文件命名共享内存，含目标状态、租约、诊断及宿主状态，常态零文件替换写盘；原 1 s／1.5 s／3 s／0.999 守卫不变）。自写 CLR 对照通过：磁盘阻断不中断实时状态，停产快照仍在 1 s 内触发 `io_stalled` 与宿主过期拒绝；全仓 914 项（605 通过、309 条件跳过、零失败）。实机 `continuous-13..16` 验证标题、新游戏加载、控制权交接与对白推进；`continuous-16` 共记录 65 条动作，包含标题、新游戏确认、等待及加载审核，并非 65 步对白；其中完整版 `continuous-16` 2,359 次共享内存观测零传输错误（心跳最大间隔 47 ms），本批未再复现 `io_stalled`／状态过期／`bridge/status.json` `WinError 32`，不能据此证明历史偶发停顿永久消除。最后一帧为全白并触发 0.999 黑白帧守卫，最终批次错误为控制期限到达（`ok=false`）；四方向自由移动与实机父进程强杀回收未验收，未宣称完整玩法验收。
