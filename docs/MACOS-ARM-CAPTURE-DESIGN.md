# macOS arm64 被动窗口采集接入设计（实施中）

## 目标与当前边界

Windows 保持主线，非 Windows 优先 macOS Apple Silicon。人工玩游戏时，工具持续截取所选窗口、留图和接受人工标记；不发送输入，不抢焦点，不关闭用户游戏。

已按持续推进授权进入实施，源码入口、随包辅助进程与冻结应用均已接通。cloud-22 的源码及冻结 AppKit 产品链已通过完整遮挡新图、冻结反例、遮挡中改尺寸、观察与人工标记并发、归档及正常退出；各独立核对 33 张 PNG。真实组件故障验收在两种形态各通过 11 项，分别回收 12 个辅助进程且无残留。Metal 仍出现重复计数，完整产品验收尚未通过；首次授权／撤权、普通用户桌面与真实游戏仍未验。直接复算留存 PNG 后，源码产品遮挡序列为 `13、13、15、21`，冻结产品为 `16、16、16、18`，两者均不满足连续增长；同批默认独立持续流也为 `27、30、31、31`。源码／冻结各记录 25／29 个呈现回调，正呈现时间戳均为 0；GPU 完成数增长不能证明窗口系统已显示新图，现有证据尚不足以在目标呈现与采集缓存间确定唯一根因。复算记录位于 `<macOS产品实施目录>/metal-evidence-review.json`。cloud-23 进一步完成 stdin 默认／async 单变量对照：源码遮挡计数分别为 `14、14、14、15`／`12、12、13、13`，冻结分别为 `17、17、19、27`／`15、15、16、16`，四组均失败。直接解码记录见 `<macOS产品实施目录>/cloud-23/independent-metal-async-comparison.json`；各组正常回收进程，AppKit 源码／冻结本批分别独立核对 32／37 张 PNG 且产品链继续通过。该结果否定“只切换 stdin 即解决问题”的假设，不足以指定唯一根因；原判据保持。

历史独立探针在 macOS 15.8.2 arm64 云端环境中发现：SCStream 在完全遮挡时停止产生 complete 帧；相同窗口改用 SCScreenshotManager 单窗口截图能获得新内容。运行 `44940206862` 已完成 AppKit 与 Metal 两组的正常、完整遮挡、冻结反例、遮挡中改尺寸及正常退出验证，并独立回读 36 张 PNG；详细计数、覆盖检查与限制见[探针结果](MACOS-ARM-CAPTURE-PROBE.md)。该证据支持选择截图路线，不能将探针当作产品交付。

公共层已有 `CaptureSource`、`CaptureFrame`、`CaptureSession.read(timeout, stop_event)` 和 `close()`，观察循环绑定来源并自动释放会话。实施工作区已纳入公共契约的已验快照；main 尚未合并，另一工作区的 9 份未提交改动原样保留。

## 推荐形态

采用一个随包提供的自写 Swift 辅助进程，使用 Apple 系统框架 SCScreenshotManager 和 `SCContentFilter(desktopIndependentWindow:)`；Python 适配器实现现有 CaptureSession 契约。辅助进程只持有采集权限和自己的资源，不接入游戏输入或游戏生命周期。当前探针仍是实验程序，不能直接改名分发为正式组件。

这条路线复用已经云端运行的系统接口，不要求用户安装 Swift 或手工编写配置。PyObjC 会引入额外依赖及冻结打包验证；通过 ctypes 自行绑定 Objective-C 对象与异步 block 会扩大维护边界。因此先推荐 Swift 辅助进程。正式打包、签名和授权归属必须单独验收，不能从命令行探针推断正常用户体验。

SCScreenshotManager 的 API 起点是 macOS 14。当前仅有 macOS 15 arm64 的实验环境证据；产品支持范围以实际验收为准。不因新增采集能力修改通用版其他功能的系统下限；旧系统进入该功能时给出明确的不可用原因，不能删除门控后空跑。

## 会话与来源

1. 通过系统可共享内容枚举窗口，界面展示应用名称与窗口标题；候选查找不得匹配后自动换源。默认只选择一个窗口。
2. 会话绑定窗口 ID、所属 PID 和该 PID 的进程启动身份。首次采集前再次确认它们一致；关闭、PID/窗口重用、权限丢失或源变化结束本会话，要求重新选择。
3. `CaptureSource.platform` 使用 `darwin`，`backend` 使用能区分单窗口截图 API 的固定名称，`source_id` 包含会话绑定身份，`hwnd` 为 None。具体编码与元数据向后兼容测试一起确定，不伪造 HWND。
4. 每次成功完成系统截图才递增序号，并记录完成时间（带时区 UTC）与调用耗时。相同内容的新截图仍是真实采集；观察层按现有规则去重。没有新结果时返回 None，不能将上次图像重新编号。
5. 尺寸来自当前窗口内容与缩放因子，保留完整窗口内容；使用现有公共裁切逻辑。窗口尺寸变化不能切换来源，不能用整屏回退代替单窗口。

## 异步边界与资源

现有观察循环调用 read 时使用至多 50ms 的等待预算，不能在调用线程中直接等待一次系统截图。Python 适配器需要后台读取辅助进程的结果，read 只等待已有缓冲区并响应 stop_event；缓存只保留最新一张未消费图像，不累积无界队列。

初始采样间隔复用观察任务配置，不预先宣称高帧率。探针每组 17 次截图调用的中位数为 AppKit 22.05ms、Metal 27.21ms，单次最大值分别为 175.92ms 和 124.46ms，因此不能用该中位数保证 read 的 50ms 等待预算。辅助进程串行发起截图，上一请求完成或超时前不发起下一次；采集超时由父进程回收自己的辅助进程，不能终止目标应用。停止、父进程 EOF、输出端断开与异常都需要同一条关闭路径。不得为平台适配放宽现有控制守卫、黑帧判据或已有超时约束。

建议使用父子进程的标准输入/输出传输请求、结构化元数据和 PNG 二进制，日志走 stderr，不另开监听端口。实现前应在协议文档里写清 framing、长度/像素上限、截断处理与协议版本，并用真实管道测试读一半退出、阻塞、损坏长度和父进程退出。协议不是已经确定的产品接口，不能复用本探针的磁盘 JSON 文件当作未经约束的生产 IPC。

## 用户入口、授权与打包

- 复用已有观察/人工标记入口。macOS 用户先选窗口，再按系统正常流程允许屏幕录制；权限不足时展示可理解的原因和恢复步骤。不得修改 TCC 数据库、自动勾选权限或静默改系统安全控制。
- GUI、CLI 和 MCP 应使用同一个平台能力判断与后端工厂，Windows 原有行为保持兼容；Linux 仍按单独计划推进，不因本任务顺带开放。
- 原生组件在 macOS arm64 构建机上编译并随便携包分发，记录源代码版本、目标架构和摘要。Python 源码运行时缺少匹配组件时明确报不可用，不在用户机器上自动安装编译器或下载软件。
- 打包应沿用现有应用结构；签名、稳定路径、屏幕录制权限归属和升级后的授权表现需真实验证。云端已有授权只证明该环境可读，不证明首次用户授权、拒绝/撤销或 GUI 跳转体验。
- 产品构建完成后必须启动冻结成品，经系统接口采集另一个进程的窗口；不能拿 Qt 自截屏或独立探针替代。

## 实施与验收批次

先合并已验证公共采集契约，再以测试驱动实现 Python 会话适配和 native helper；所有操作在新的隔离工作区进行，不叠加或覆盖现有工作区未提交内容。

本地覆盖来源绑定、正常帧、空结果、旧序号、流截断、损坏 PNG、权限拒绝/撤销消息、窗口关闭、取消和幂等关闭，确认不导入 Win32。云端以真实辅助进程贯通目标查找→截图→公共观察循环→PNG/时间线归档→人工标记→正常停止；分别跑 AppKit 和 Metal 自写窗口的正常/完全遮挡/冻结反例/改尺寸，检查普通桌面焦点未变化与进程全部回收。随后构建并运行 arm64 冻结成品，核对组件摘要与同样的观察链。

首次授权/拒绝/撤销、普通用户桌面、真实 GPU 游戏、最小化、长期稳定性和 macOS 14 兼容性分别验收；没有环境证据的项目明确保留未验。不能将本设计或自写窗口通过写成全部游戏已支持。

## 已采用的取舍

按“Swift 随包辅助进程 + SCScreenshotManager 单窗口按需截图 + 现有公共观察契约”实施；保持 Windows 主线，macOS arm64 单独验收。老师已授权依路线图持续推进，无须在常规实施阶段重复审阅。AppKit 在源码与冻结产品链已有实证，Metal 重复计数仍按失败保留；cloud-22 将独立探针与产品统一为 0.35 秒取样后，持续流和单张截图仍重复，采样间隔不能解释全部失败。下一批必须先有新的可测假设，不能盲改重跑；cloud-23 默认／async stdin 四组对照均失败，不重复同一开关。首次权限授权、安全控制及真实游戏范围仍按既有批准边界执行。
