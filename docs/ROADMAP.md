# 游戏 QA 工具长期演进路线

## 目标与使用场景

用户希望 AI 能操作游戏完成测试，同时自己仍能正常使用电脑。工具应减少重复截图、逐图复核和手动整理证据的劳动；换游戏不应重写整套系统。

本文件是可持续修订的暂定思考与路线，不是冻结的完整设计，也不代表所述能力已经实现。用户已授权继续推进可验证部分；新安装、原游戏注入及不清楚的存档写入仍需先明确边界。后续阶段先做实证、再调整方案。实际交付与验证以根目录 `CHANGES.md` 为准。后续会话先读本文件和最近的变更记录，再检查当前代码及 MCP 工具列表。

## 当前共识与工作假设

后续优先补缺少的引擎／后端及通用入口。已有适配通过后台运行、输入隔离、连续新画面、正常操作和暂停释放验证后，按已测范围收口；战斗、存读档、全流程与长期稳定性按具体任务追加，不作为转向其他引擎前的必清项目。Wolf 基础桥已收口，暂不追加该引擎的玩法跑批。

1. 本仓库集中维护游戏测试软件、MCP、巡检 Skill 和后续适配插件，便于寻找与持续迭代。Skill 源码放在 `skills/`，不分散到另一个技能仓库；全局发现入口与源码维护位置是两回事。
2. 保留 `game-qa-kit` 和现有 MCP，基于可工作的实现增量改进，不另造一套控制台。
3. 借鉴 `bugwatch` 的异步分析、疑点筛选、事件归档、去重及统计；不是把两个项目整体合并。
4. **观察与控制是两条独立能力线。** 不抢焦点的后台截图，不等于后台输入可用；疑点筛选完成，不等于后台操控完成。
5. 引擎内部输入是首选方向。用户此前没有 Unity 外部控制插件；Unity 适配由本项目实现，优先复用可验证的公共工具与已有 RPG Maker 接入经验。
6. 可以评估 YOLO 做弹窗等视觉对象筛选，结合文本校验、AI 收集整理和人工/AI 复核；不是默认排除 YOLO。当前不自动安装依赖、下载权重或启用未知模型，尚未选定具体权重。
7. 保留人工手玩与标记能力。自动筛选只是安排复核优先级，不能丢掉所有普通画面或把候选直接当缺陷。
8. 不以通用 `PostMessage`、第二显示器或恢复鼠标位置冒充输入隔离。

## 第一阶段：融合 bugwatch 的证据处理能力（已完成本轮范围）

### 实施边界

- 在原有画面变化留图之外，增加独立、容量有界的分析队列；分析慢不能阻塞正常采集。
- 默认用窗口可读文字筛选报错候选；可选 OCR 分析画面文字。OCR 不可用时明确降级，不能阻塞留图。
- 用于汉化的初步规则只提示连续假名、替换字符等候选；繁体汉字不直接认定为日文。
- 同一窗口同一持续异常合并为事件；异常消失后再次出现，应能重新记录。
- 疑点保存原图、时间、窗口、截图区域、原始文字、分类依据及“待复核”状态；普通留图继续使用既有 dHash 提示。
- 展示采集数、留图数、分析数、丢弃分析帧数、疑点数、队列积压及错误。dHash 不能证明没有遗漏。
- GUI 与 MCP 共用会话控制逻辑；同一 profile 不允许重复启动采集。
- MCP 补齐 `watch_start`、`watch_stop`、`watch_status`、`watch_events`，保留既有工具与危险操作确认。
- 停止请求不阻塞 GUI/MCP；排空有限分析队列后才能报告已停止。读取疑点须分页，避免占满上下文。
- 原会话、截图、存档不迁移、不删除。新会话不能覆盖旧证据。

### 第一阶段不做

不修改现有点击/按键行为，不注入真实游戏，不修改存档，不承诺后台操控；不训练检测模型，不加入未经验证的 YOLO 分类。

## 人工测试与 AI 操作长期并存

用户明确要求保留人工盯屏：自己也会手动玩游戏进行测试。人工模式不是待删除的过渡方案。

- 人玩时：观察链只采集、留图、人工标记与整理疑点，不发送输入；现有入口继续可见。
- AI 玩时：由后续适配插件发送动作，继续使用同一条观察/证据链，不复制另一套留证系统。
- 后续接入 AI 控制时，必须提供暂停 AI / 人工接管；停止排队动作、释放按键，再交给用户。恢复 AI 要明确继续，不能仅切换标签。
- 不因用户正在操作电脑而擅自开启前台输入。人工标记与自动候选都保留各自来源，复核不混淆。

## 进程选择入口（已实现）

参考 bugwatch：新建/编辑配置时刷新运行中的窗口，显示程序名、PID 和标题，选择后读取程序路径与可用尺寸。
最小化的游戏仍可选择，不自动恢复或抢焦点；无法读取的尺寸明确未知。存档位置、输入能力和引擎类型仍不从进程名臆测。

配置持久化程序路径，PID 只绑定当前会话。严格路径约束覆盖截图/标记及既有 MCP 输入的目标选择；同路径多实例而没有 PID 时拒绝猜测。
此入口降低建配置成本，但不是引擎插件、自动存档发现或后台输入隔离。

## 第二阶段：后台控制的最小实证（SDK 与当前 VX Ace 定制游戏副本已验证）

### 必须同时打通的三条链

1. **输入隔离**：AI 动作只进入目标游戏，不移动系统光标、不影响其他应用；用户在其他应用打字也不干扰游戏。
2. **后台运行**：游戏失焦后逻辑继续更新；按下、保持、松开的状态不会被焦点逻辑错误清掉；断线或停止时释放按键。
3. **画面获取**：窗口被遮挡时仍能得到新的游戏画面。最小化是否支持必须单独测，不与“被遮挡”混为一谈。

### 验证样本

用户调整后的顺序：先常见引擎，后补八星帝等尚未适配的游戏；不把“以前忘记写插件”等同于引擎已经证实难以适配。

1. **当前运行的 RPG Maker VX Ace**：`Game.ini` 的 `System\\RGSS301.dll` 与 `Data\\Scripts.rvdata2` 确认 RGSS3/Ruby。已只在完整隔离副本插入桥，正常读取获准的 7 号档并验证移动、菜单、截图及暂停；原游戏未注入，9 号档未复制或改动。其自定义 `Graphics.frame_count` 在初始化前不可用，桥只使用自身更新计数，避免依赖它。
2. **RPG Maker MV/MZ 家族**：共用协议与可复用实现，差异独立适配；不能把 VX Ace 的 RGSS3 插件与 MV/MZ 的 JavaScript 插件混为一体。
3. **Unity**：旧 Input、新 Input System、IL2CPP/新输入和 Mono/Rewired 已有分后端实现与相应实测记录。继续扩展实际玩法验收、IL2CPP 旧输入／中间件及动态程序集等未覆盖组合；每款游戏先核对保存边界，不以商业副本的菜单／剧情通过推断全部操作兼容。
4. **《八星帝》HSP**：首版已完成上述空白工程与商业标题／读取菜单实证，使用同一份外置字节码和本机官方 HSP 3.7 运行时，原游戏未注入、原存档未复制。原内嵌 EXE 不读取旁边修改的脚本，必须按 `plugins/hsp/README.md` 准备隔离副本；`profiles/rai8.json` 为历史配置，不能直接据它认定当前测试目标或兼容范围。玩法与其他运行时另验。

每次先做小样本实证。改游戏、注入或改存档前说明具体范围、风险与可还原方法；存在影响结果的理解分歧先问用户。

### 实证记录

每个样本记录引擎/版本、控制方式、后台逻辑是否继续、遮挡/最小化截图是否更新、是否干扰用户输入、命令失败率和延迟。没有实测数据不承诺节省比例、兼容范围或性能。

## 第三阶段：主程序统一协议＋低耦合适配插件（v1 实验实现，扩展中）

### 接口方向

**上层命令只有一套，不为每个引擎另造 MCP 命令。** 例如 AI 下发“移动”，主程序识别/选择当前模块；RPG Maker 插件把它翻译为对应引擎的移动输入，Unity 插件走其内部输入路径。插件只面向主程序，不互相调用、不依赖彼此。

统一接口已实现移动、确认、取消、等待等动作；按帧输入和画布点击按实际能力开放。主程序统一状态、结果、暂停与恢复；具体工具和协议见 `docs/MCP.md` 与 `docs/BACKGROUND-CONTROL.md`。v1 已有实验实现，兼容范围仍以样本实测为准。

- 主程序负责统一协议校验、当前目标与模块选择、调度、超时和证据，不包含散落的引擎输入实现。
- 插件负责引擎/游戏动作翻译、内部控制、后台运行适配以及可提供的画面/状态通道。
- 能力发现返回该插件实际支持的动作、后台运行、输入隔离和截图状态。缺能力时明确拒绝，不能悄悄改走桌面输入。
- 主程序调用统一接口，不暴露一套 `unity_move`、另一套 `rpg_move`。插件互不导入；更换插件不要求改其他插件。
- MV/MZ 可共享 RPG Maker 家族适配的公共实现，差异留在版本适配层；其他引擎分开。游戏定制键位/插件覆盖不能硬塞进公共逻辑。

优先级：复用用户已有实现 → 复用可验证的现成插件 → 最小引擎适配 → 最后才补游戏特例。

Unity 需区分旧输入与新 Input System、Mono 与 IL2CPP。RPG Maker 需区分 MV/MZ 和更旧版本；游戏自带插件可能改变输入与暂停行为。通用的是上层协议，不是万能注入点。

### 操作与证据形成闭环

命令携带唯一编号，在游戏线程中执行；返回是否真正消费、执行帧以及动作之后的新截图。必要时返回当前菜单、按钮位置、对话/场景等可读状态，减少视觉猜测。

超时或状态不明时先查询结果，不盲目重发非幂等动作。截图失败、停更或连接断开时暂停自动操作；不得悄悄退回抢前台输入。

通过正常输入触发游戏行为，不直接修改“任务完成”“场景已切换”等结果来冒充测试。读取内部状态可帮助定位，不能替代实机画面证据。

## 第四阶段：不适配游戏的隔离兜底（独立 Win32 Desktop 已做实验，其余待验证）

用户提出把游戏统一放在模拟/隔离环境中，让 AI 使用该环境自己的鼠标、键盘和桌面，环境保持运行并挂在主机后台。可评估独立机器、虚拟机、Windows Sandbox；这是一种输入/画面适配后端，不应让上层命令随环境变化。

必须先核对所指 Python “virtual desktop” 包的实际能力。已核实 `pyvda.VirtualDesktop` 用于任务视图桌面管理，单独使用不提供独立键鼠。`CreateDesktopW` 是当前已验后端，不是产品必须采用的技术；可替换方案需重新通过后台运行、新画面、输入不互扰与暂停释放验收，并适配现有桥的桌面身份检查。方案及一手来源见[轻量后台控制调研](BACKGROUND-ALTERNATIVES.md)。

GPU、后台渲染、性能、反作弊、授权、存档持久化和异常退出恢复必须逐项验证。Sandbox 的环境/数据生命周期也要先确认。不提前保证可用，不擅自安装软件或修改系统安全设置。普通多显示器仍共用输入焦点，不是隔离方案。

本机只读预检确认当前为 Windows 11 家庭版，Sandbox 入口不可用；微软明确该版本不支持 Windows Sandbox。已有 VMware 及四份 Linux 虚拟机记录只作为环境事实，不再作为默认推进方向，不创建 Windows 虚拟机。证据留在 `<隔离预检目录>/environment.json`、`vmware-paths.json`、`registered-vms.json`。

## YOLO 的启用门槛

YOLO 是目标检测模型，不是通用故障判断器。轻量版本是否足够，要看权重、类别、图像尺寸和硬件，不只看模型名称。

只有明确“要检测什么对象”、已有样例且现有规则/OCR 存在可量化不足时，才评估权重。记录来源/许可、下载大小、推理耗时、误报和漏报；与不启用 YOLO 的基线比较。模型输出仍为候选。

## Skill 与工具同步

本轮同步方向：先发现实际工具能力；人玩和已验证的 AI 控制分别适用；长驻盯屏后分页复核疑点，不逐页重复截图；缺少后台能力就明确报告，不擅自抢前台或强制输入。保留截图证据门、候选/缺陷区分、同形字规则和改档可还原规则。

## 适配经验沉淀为插件开发 Skill（已收入首版，持续迭代）

## 长期验收与迭代纪律

- 分别验收“记录复核省事”和“AI 后台操作”，不能用其中一项替另一项结案。
- 自动无疑点不等于游戏无缺陷；分析队列丢帧必须可见，并留普通帧供补查。
- 以用户真实任务衡量：手工整理时间、模型往返次数、错误操作、输入干扰和证据完整度；不预设未经测量的目标数值。
- 每轮只解决有证据的瓶颈，优先局部改进，不为了架构完整堆适配器。
- 新需求先更新本文件的相应阶段；实现完成且验证后，更新 `CHANGES.md` 和执行清单。
