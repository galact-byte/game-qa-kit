# Artemis 自写场景后台预检

本记录对应固定 Windows 构建的进入条件和后续受管验证。当前只接登记自写场景的右移与等待；商业游戏及其他构建不在支持范围内，操作入口见[插件说明](../plugins/artemis/README.md)。

## 已确认的条件

- 本地候选为《背徳の衝動》ver1.10 的目录，存在运行程序、脚本、资源包和保存配置。只读核对不等于已验证商业游戏完整可玩，本批没有启动商业入口。
- `HaitokunoShoudou.exe` 的 SHA-256 为 `4480a20da5857ea329036c3031e671241f5efb73e9f75bf07412834d3c0a60b2`。
- 原 `system.ini` 在 `[WINDOWS]` 节使用 `BOOT=system/main.iet`，以相对路径 `savedata` 配置保存目录，并提供 `FORCE_SOFTWARE_RENDER` 开关。原脚本存在 IEScript 图层、过渡、位置与 Lua 标签。
- 独立副本只复制运行程序与 `d3dcompiler_47.dll`，另写配置、脚本与自绘图片。副本未携带商业脚本、图像或 `root.pfs`。窗口出现自写脚本指定的标题，证明固定运行程序能够执行自写 BOOT。

## 历史零输入结果

通过现有 `DesktopProcess` 的独立桌面与 Job Object 启动；没有输入投递、二进制修改、插件注入、实体光标移动、软件下载或安装。

| 批次 | 本批区别 | 结果 |
| --- | --- | --- |
| `zero-input-01` | 自绘 PNG、精确匹配 640×480 客户区 | 实际窗口为 512×384，探针未匹配；没有取图和输入，不能单独作为绘制失败证据 |
| `startup-diagnostic-01` | 观察首批副本的真实窗口与首图 | 类名 `Artemis`、自写标题成立；生产取图层判定 100% 黑帧并停止 |
| `zero-input-02` | 按窗口类与宽高比选窗；改用样本已有语法的纯色图层 | 首图 100% 黑帧；取图早于自写标题出现，保留准备阶段歧义 |
| `zero-input-03` | 等待自写标题出现 | 脚本已执行后的首图仍为 100% 黑帧，停止 |
| `zero-input-04` | 仅增加原配置已有的软件渲染开关 | 首图仍为 100% 黑帧，停止 |

历史失败批次完整保留。三次修正仍失败后曾停止，后续依据样本中明确存在的日志和引擎截图标签进行分层取证，没有沿用猜测接口试跑。

## 后续分层取证与干净复验

| 批次 | 证据与结论 |
| --- | --- |
| `script-log-01` | 自写脚本日志确认两次图层过渡及中间 1.2 秒等待均已执行，没有错误或警告；排除脚本停在标题之后的假设 |
| `render-export-01` | 用样本已有的 `takess`／`savess` 标签导出引擎合成画面；两帧均有自写色块，每帧 2,501 像素，左边界从 x=80 到 x=180，证明图层和定时更新成立 |
| `capture-compare-01` | 生产 `PrintWindow` 与窗口 DC 两路均取得有效自写画面，未复现历史黑帧 |
| `capture-log-only-01`、`capture-export-only-01`、`capture-clean-01` | 逐项撤去日志或原生导出，进一步核对诊断副作用；这些批次用于解释取证，不增加控制覆盖 |
| `clean-recheck-01`～`03` | 恢复原第四批的自写脚本、配置与生产取图流程，保留软件渲染配置，不启用日志或原生截图。三个独立副本全部取得两张有效截图：每帧色块 2,501 像素，左边界 x=80 → x=180 |

三批干净复验只改变证据目录和副本名称。新副本的 `probe.iet`、`system.ini` 与历史第四批逐字节比对，运行程序摘要一致。生产取图层的 99.9% 黑白帧判据、三秒取图期限与十五秒启动期限均未放宽，生产代码没有修改。

此前三批可以确认固定构建在自写场景中曾于独立桌面持续取得更新画面。**后续 `clock-probe-01`～`03` 在新的零输入场景再次遭遇生产首图无效（100% 黑／白像素）；过去成功不能推断当前启动稳定，根因仍不明，没有修复提交。** 色块位移来自脚本定时更新，不能作为按键输入生效的证据。

各批原目录前后 **1,127 个文件**的 SHA-256 一致，测试目标均由 Job 回收；最终审计重新核对原目录和任务进程。自写副本新建的保存数据与原存档分别保留，无需覆盖原目录还原。该核对不覆盖系统全盘、注册表或任意外部持久化位置，独立桌面不等同文件系统隔离。前台只记录前后句柄，不据此声称全程前台不变。

## 输入接口取证与自写实测

此前只读脚本和公开介绍不足以证明虚拟输入接口。本轮 REA 的 IDA 后端实际可用；针对同一固定 EXE，Lua 注册、反编译与覆盖表读写调用链核对表明，`overrideKey` 接收 `key`／`status`，写入正常 `isDown` 查询读取的引擎输入覆盖表。完整二进制分析产物只留本地，不入库。这些证据取代前一阶段“无可用深度分析后端／接口待证”的当前判断，历史记录保留。

三个新增批次只用独立自写副本，没有运行商业场景：

| 批次 | 结果与界限 |
| --- | --- |
| `input-probe-01` | 单次覆盖令普通输入查询为真，色块 x=80→82，后续恢复为假；持续按住断言失败，保留原始失败，不当作持久按键接口 |
| `input-probe-02` | 每次采样前重申覆盖；持键两图 x=84→104，松开后两图均 x=110；通过 |
| `input-probe-03` | 持键／松键重申移到 `onEnterFrame` 回调，普通场景循环独立查询 `isDown(39)`；持键两图 x=86→106，松开后两图均 x=110；通过。`clear` 清理仍由普通循环执行，不代表已验故障释放 |

两批成功输入探针都先取有效首图再发送本地探针命令，截图每帧色块 2,501 像素，按住才由正常查询驱动移动。原目录 1,127 个文件摘要一致，任务目标已退出。只有前后台句柄记录，不宣称全程前台身份采样或真人并发已经通过。持键时间由本地探针安排，未接统一 MCP、正式租约或受管入口。

## 设计获批后的历史受阻批次

老师已批准[脚本桥设计](ARTEMIS-ADMISSION-DESIGN.md)。以下三批仅在新建自写副本验证 `now` 的返回形状与计时语义，未投递输入，当时尚未实现产品插件。

| 批次 | 区别与结果 |
| --- | --- |
| `clock-probe-01` | 静态色层和 250 毫秒等待循环；`now` 返回数值，但生产首图被拒绝为 100% 黑／白无效帧，未进入 CPU／停帧比较 |
| `clock-probe-02` | 增加原生画面导出，并等至少四条目标日志后取首图；合成图有 2,501 像素标记、左边界 x=80，窗口首图仍为 100% 黑／白无效帧 |
| `clock-probe-03` | 保持第二批诊断条件，仅在采样循环增加已使用过的 `trans` 提交；原生图标记仍完整，窗口首图仍为 100% 黑／白无效帧 |

三个批次均在首图失败处停止，未挂起目标、未投递输入；Job 回收后目标退出，原目录 1,127 个文件前后及最终重新核对摘要一致。原生导出证明引擎内部已有合成画面，不能替代生产窗口截图，也不能证明窗口实际呈现正常。拒绝回执只给黑／白像素合计比例，没有保留被拒窗口帧，不能进一步确定是纯黑还是纯白。本轮未定位窗口输出与后台取图之间的具体故障。

## 新增边界证据与计时／撤销验证

受阻后没有降低判据或重复同条件动作测试。`capture-boundary-02` 新增窗口身份、子窗口、独立桌面绑定及两条取图路径观测：客户区为 512×384，无子窗口；取图线程绑定目标桌面；生产 PrintWindow 和窗口 DC 均得到蓝底与 2,501 像素标记，黑／白比例为 0。本批通过有效首图门槛，但不能解释先前偶发无效首图，也没有对应取图修复。

`clock-probe-04` 在有效首图后比较目标计时、宿主单调时间与进程 CPU。静态调用链为 `timeGetTime` 并清除最高位；1.703 秒挂起期间目标没有新采样且 CPU 不增长，恢复首条目标毫秒值比挂起前增加 1.779 秒。含义是挂起时不能查询或发布新值，恢复后时钟包含停顿时长，不能把它描述成暂停推进的 CPU 时钟。桥使用模 2³¹ 的目标毫秒期限，回调次数不作时间单位。

`expiry-probe-02` 先取得有效首图后实测：持键两图 x=84→94，有限动作自然到期后两图均 x=98；短停帧恢复不消费已过期持键，短读撤销覆盖。七帧每帧 2,501 像素，正常 `isDown` 查询与画面对应。原目录 1,127 文件摘要一致，进程回收。

## 正式脚本桥与受管实测

`plugins/artemis/` 已实现 Lua 状态机、严格有界文件通道、固定源准备器、共用 Supervisor／DurationSession 宿主与受管登记。只发布 `right` 和 `wait`，动作使用协议 2 的毫秒单位。正常场景查询后才发布按下或松开的消费回执；心跳不延长单次动作截止时间。暂停仅停止合成输入，不暂停游戏仿真。

早期受管测试暴露了两个确定问题：窗口筛选错误地要求 640×480；原子替换同名输入文件时，目标 CRT 打开会收到 `Permission denied`。现按有效客户区选窗，双向通道改为逐代只发布一次；尚未读入的新命令短暂不可打开时保留当前记录及原期限，当前记录缺失或短读仍撤销输入。旧消费记录处于删除中的权限错误不阻挡新记录，也不刷新活性。以上修正不声称解决历史首图偶发异常。

| 验证 | 结果与界限 |
| --- | --- |
| `managed-09` | 源码真实 MCP 7 项和真实引擎 Lua 状态机 1 项通过；Lua 用例内部 22 条状态规则全部通过 |
| `portable-managed-01` | 冻结 `GameQA-MCP.exe` 的 7 项真实 MCP 用例通过；与源码使用同一受管测试 |
| 正常生命周期 | 暂停有效首图、恢复、右移消费与释放、两次等待位置稳定、重复动作不重放、人工暂停／恢复、正常结束与源文件核对 |
| 故障生命周期 | 过期请求、空闲租约到期、双会话输入／回收隔离、截图故障后确认释放、目标停帧后的释放未确认及 Job 回收、MCP 强制结束后的进程树回收 |
| `visual-managed-01` | 真实 MCP 有限持键五帧 x=80、84、90、98、98，每帧 2,501 像素；按下／松开消费分别来自目标采样 8／17。143 次前台采样未见目标游戏占用用户前台；不等同真人键鼠并发验证 |

目标停帧或创建者被强制结束时，不把进程退出冒充游戏已消费松键；已观察到的按下和未确认释放分别保留。所有首图无效批次零动作停手，1.5 秒租约、1 秒停帧／释放、3 秒截图、15 秒启动及 99.9% 黑白帧判据保持。

## 当前范围与后续

固定运行时＋登记自写场景的源码／便携受管通路已验，历史首图偶发异常仍未归因。商业启动与玩法、其他构建、其他方向、菜单、鼠标、存读档、音频、长期稳定性和真人并发未验。不能将短时成功写成引擎全面支持或稳定性保证。后续若涉及商业场景改造、原生加载器、注入、软件下载或系统级诊断，仍须按对应边界另列范围与还原方法。

## 证据与回退

原始脚本、配置、截图、前后文件清单、窗口记录和拒绝回执位于 `<Artemis预检目录>/preflight-01/`，不随源码入库。`VERIFICATION.json` 保留历史首图受阻阶段的审计；`FOLLOWUP-VERIFICATION.json` 是后续分层取证和三批干净复验的审计；`INPUT-VERIFICATION.json` 与 `audit_input.py` 核对本轮三个输入批次、失败保留、像素／摘要、原文件和进程收尾。审计通过表示记录与证据一致，不代表正式控制接入通过。`CLOCK-VERIFICATION.json` 与 `audit_clock.py` 记录三个前置验证失败批次及新鲜收尾核验，`runtime_passed=false`。继续前读取同目录的 `RESTART-HANDOFF.md`，不要覆盖既有批次。

本轮代码、样本和说明随仓库交付，运行组件与原始证据不入库；来源及许可见[来源说明](../plugins/artemis/SOURCES.md)。新增边界／时钟／到期批次、`managed-09`、`portable-managed-01`、`visual-managed-01` 和最终审计分别保留，历史 `runtime_passed=false` 不回写成成功。停止旧会话、回退插件与受管登记并重新准备即可回退；原游戏不需存档迁移。
