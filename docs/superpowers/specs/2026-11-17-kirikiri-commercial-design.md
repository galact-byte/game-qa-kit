# KiriKiri 固定商业 KAG 接入设计（待批准）

状态：设计草案，仅完成静态证据核对，尚未实现、创建商业运行副本或启动商业游戏。本文的“必须”“拒绝”“通过”描述实现及验收要求，不表示已有这些运行能力。

## 目标与批准范围

为[已审查的固定商业样本](../../KIRIKIRI-COMMERCIAL-BOUNDARY.md)提供受限实验入口：保留商业 KAG 原初始化、剧情、输入与保存逻辑，先验证真实 Enter 输入及目标松键，再决定是否扩展玩法。产品识别保持 `adapter=null`、`control_verified=false`；本设计不接通用 `game_prepare`、GUI 或其他 KiriKiri 构建。

建议先批准本设计的实现及自写夹具验证。商业三文件复制、注入与单批启动另行批准；任何实际启动清单须在自写验证完成后列明，不将本设计审批视为商业运行授权。原目录、原存档、安全软件、系统采集及发布流程均不属于实现范围。

选择：在固定 x86 运行时主线程恢复前安装进程内原生写入守卫，商业 KAG 的输入桥通过已有 `AfterInit2.tjs` 扩展点加载。仅做 TJS 路径检查无法保护早期日志与原生插件；当前也没有证据证明 `wuvorbis.dll` 的 CRT 写路径不可达。不引入新的操作系统隔离产品或账户／ACL 配置。

## 已有依据与尚未证明的部分

- EXE、`data.xp3`、`wuvorbis.dll` 三个摘要以商业边界文档为准，任何一个不匹配即拒绝准备。EXE 固定为 2.32.2.426／x86；版本字符串相同不能替代摘要。
- 原归档 `startup.tjs:6` 执行 `system/Initialize.tjs`；后者在 `234` 行创建 `global.kag`，`263-266` 行依次加载原 `AfterInit.tjs` 和 `System.exePath + "AfterInit2.tjs"`。使用明确的绝对位置扩展点，无需重打 XP3 或猜测同名脚本覆写优先级。
- `AfterInit2.tjs` 晚于配置检查与窗口构造。因此它只承担输入桥加载、路径断言与就绪报告，不能承担初始化之前的写入防护；外置扩展点实际生效仍须运行验证。
- 音频 DLL 对 `WriteFile` 导入地址的静态引用去重后是三个指令位置：一个位于 CRT 错误输出 `_NMSG_WRITE`，两个位于 CRT 文件描述符写入 `_write_lk`；`FlushFileBuffers` 引用位于 `__commit`。错误输出使用标准错误句柄，文件描述符路径使用 CRT 句柄表。这说明需要约束句柄来源，不能以“未导入 CreateFile”替代保护。
- `wu_ov_open_callbacks`、`wu_ov_read` 只是向内部函数转发的导出包装；当前证据没有穷尽所有宿主回调、间接调用与异常路径。已定位 CRT 写入不等于插件只读，不继续把完整不可达证明作为接入前的无限调查任务。
- 现有 `plugins/native_input/StartupGuard.hpp`、`Host.cpp` 提供挂起启动、调试期守卫和 Job 回收的参考；`WriteGuard.hpp` 当前主要拦截文件创建／打开及部分注册表修改，不能直接作为本设计全部写入保证的已验实现。不得放宽既有 SRPG 样本哈希或悄悄改变其运行策略。

本地证据位于 `<KiriKiri验证目录>/commercial-boundary-01/native-write-followup-bundle` 与 `native-write-followup.json`。反编译文本、原游戏与证据包不入库。

## 启动与保护顺序

1. Python 准备器只读核对固定三文件及部署清单，建立全新会话；独立诊断桌面承载目标窗口，避免启动弹窗影响当前桌面。
2. 专用 x86 启动宿主以挂起状态创建目标，禁止继承未列明句柄，立即加入关闭即回收的 Job。子进程环境与工作目录明确指向本批，不能复用 SRPG 的固定路径、哈希或输入钩子。
3. 在恢复目标主线程前，安装启动期及持续写入守卫，取得绑定 PID、会话与守卫构建摘要的就绪回执。DLL 早期初始化同样需要覆盖；不能先执行商业脚本再补装守卫。安装失败、签名不符或就绪失败都在零动作状态回收 Job。
4. 主线程恢复，保留原归档启动链。新建 `game/AfterInit2.tjs` 仅验证会话配置、原 `kag` 及输入方法存在，执行自有桥脚本并报告绑定身份、窗口与实际保存目录。不得重放或取代原 `AfterInit.tjs`。
5. Python 控制宿主核对观察、守卫状态与最新有效首图；任一不符则拒绝输入并按既有期限回收。首图为无效黑／白图时零动作，不尝试按 Enter“唤醒”。
6. 只有操作方显式恢复后才接受原 v2 的 `confirm`／`wait`。观察、截图和证据采集不抢前台。暂停仍需目标确认松键，失败按既有释放期限回收；不改为无期限等待或延后回收。

现有 `plugins/kirikiri/host.py` 的自写夹具入口继续保持严格校验。商业入口另设显式准备模式及固定摘要清单，不能简单移除夹具限制后让任意包启动。共用逻辑仅按必要程度提取；若需要改变共用控制协议，须另列变更并同步所有相关桥，本设计默认不改协议。

## 写入守卫契约

该守卫是针对固定已审查构建的进程内限制，不是完整 Windows 沙箱。它不能保证恶意直接系统调用、内核行为或系统服务自身缓存都被拦截；验收结论必须保持这一范围。若实现无法满足下列固定样本要求，保持商业启动关闭，报告具体缺口，不自行改成更宽松规则。

- **允许位置**：仅上述运行数据目录和目标负责的 `bridge/` 文件。游戏输入、桥代码、原游戏目录及副本外的证据均不可写；只读系统 DLL／字体等正常读取另行允许。
- **按最终对象判断**：同时核对创建／打开的写权限和处置方式、已有句柄的写入与截断、删除、重命名／替换、硬链接及可写映射。路径必须按最终句柄及父目录解析，检查目录边界和重解析点；词法前缀匹配不足以证明安全。重命名须核对源与目的，不能只检查打开路径。
- **句柄来源**：禁止继承外部可写文件句柄；标准输出／错误只允许本批可控目标或无效句柄。后续复制／获取外部可写句柄与映射须拒绝或验证最终目标。CRT 的 `WriteFile` 即使不经过 TJS 也受同一规则约束。
- **启动早期**：覆盖运行时／DLL 初始化及早期错误日志；守卫未确认就绪之前不能恢复应用主线程。测试必须区分守卫安装线程和应用初始化线程，不能以回执文件存在代替时序证明。
- **配置与注册表**：禁止目标修改原用户注册表；`.cf`／`.cfu` 只能落在本批。拒绝配置迁移／编辑窗口与自由文件选择的越界结果，不自动替用户点击确认。TJS 层提前检查仅改善错误定位，最终拒绝不能依赖 TJS 包装不可被覆盖。
- **外部执行**：首批不允许商业脚本启动额外子进程／外部工具；Job 的进程上限与创建拦截需要自写用例验证。遇到未知外部执行要求中止，不扩大许可。
- **失败处理**：拒绝请求返回正常失败语义并记录有限长、有限数目的路径与调用类别，宿主在原保护期限内回收；不因审计写盘卡住输入释放或租约检查。守卫被替换、记录发布失败或身份变化均使会话失效。

拟复用现有启动守卫的已验部分；额外文件操作、句柄检查和更窄目录策略放在 KiriKiri 专用组件，先不改变其他引擎默认行为。新增原生代码的来源、许可证及构建清单须随实现记录。

## 输入桥与消费证据

只开放 Enter 确认与等待；按下／松开通过 `Window.postInputEvent` 交给商业 `kag` 原 `onKeyDown`／`onKeyUp`，保留原异常与返回语义。`System.getKeyState` 仅为合成 Enter 提供有限覆层，其余键回原查询；被替换或失联按现有规则失败，Timer 序号不当作真实帧。

当前自写桥与宿主依赖夹具的 `window.value`、`window.handlerQuery`／`handler_query`，不能复制进商业入口。商业消费回执应记录事件身份、原处理器返回、覆层状态与处理器执行期间真实发生的 Enter 查询；若原处理器没有查询，不伪造查询证据。目标处理器返回证明投递被分发，实际玩法消费还必须由操作前后画面／可观察正常 UI 状态变化确认。不得设置剧情变量、调用存档函数或跳场景来造出变化。

输入暂停仅停止自动输入，不停止游戏仿真或观察。保持原启动、租约、停滞、截图、释放期限及黑白图判据；多窗口、鼠标、长时间稳定性与实体输入并发不纳入本次完成条件。

## 实施顺序与自写验收

先为下列行为建立失败用例，再做最小实现并回归。生成的自写运行目录和原生测试产物只放验证目录，不带商业正文。

| 顺序 | 验证对象 | 通过条件 |
| --- | --- | --- |
| 1 | 准备器 | 固定摘要匹配；哈希错误、额外文件、已有会话、原目录别名与空间不足均拒绝，拒绝时零启动 |
| 2 | 原生守卫 | 自写目标的正常本批写入成功；绝对／父目录／前缀同名路径、重解析点、RootDirectory 相对路径、外部句柄、CRT 标准错误、截断、删除、重命名、硬链接及可写映射越界均失败；受保护哨兵内容和元数据保持 |
| 3 | 启动与失败 | 自写 EXE／DLL 初始化尝试越界写入被挡；未就绪、钩子安装失败、目标退出与守卫失效零输入并回收；不启动商业 DLL 做此测试 |
| 4 | KAG 形状的自写 Window | 按已查加载顺序先保留原 AfterInit，再运行外置 AfterInit2，桥只绑定一次；无效 kag／多窗口／被替换处理器拒绝，不依赖 fixture 特有字段 |
| 5 | 正常输入与生命周期 | 原处理器消费按下和松开、正常画面变化、暂停新图、去重、租约／UI／释放故障回收、截图失败与原生宿主退出；沿用原期限与判据 |
| 6 | 相邻回归及静态核对 | 原自写 KiriKiri 入口与受影响共用宿主测试保持；若复用原生公用组件，补对应 native-input 回归；构建来源、文档链接、原始文件摘要和任务进程检查通过 |

自写验收通过后，交付实际构建摘要、失败证据、尚未覆盖项及一份精确商业批次清单，请求单批批准。商业首批建议限：启动→有效首图→正常确认事件至可观察 UI／对白变化→目标松键→退出；实际动作上限和可识别画面须在申请时锁定。首批不带存档、不验证商业保存、失败不自动重跑，不能把自写通过写成商业适配通过。
