# 受限原生后台输入后端设计

状态：待用户审阅，尚未授权正式实现。本文件提出的协议字段、目录和命令参数均为设计，不是现有 API。

## 1. 目标与已知依据

让 AI 在后台操作游戏，同时用户正常使用电脑，双方键鼠互不串扰。继续使用主程序、统一 MCP 和现有证据链；实现语言不是约束。

已批准并完成的实验与正式产品接入分开：

- 自有 x64 窗口已通过三条输入路径、截图、退出释放及有限实体键鼠并发检查。
- 自有 x86 DirectInput 程序已有 10 项检查；固定 SRPG Studio 构建已通过后台「标题 → 环境设置 → 返回标题」，6 条动作、8 张截图、8 条输入事件被读取。
- 固定游戏 EXE SHA-256：`8e123a4c07cfbc9143c266faf87bb66ef3600ab1254ee6d294fbaf685bb502a7`。
- 游戏实体并发、鼠标、玩法及存读档尚未验收；原型没有真实游戏帧同步或冻结游戏循环的证据。
- 证据索引：[原型实证](../../BACKGROUND-ALTERNATIVES.md#x86-directinput-与真实游戏原型实证)、[引擎覆盖表](../../ENGINE-COVERAGE.md)。原始材料在 `<Proto原型目录>/x86-directinput/`。

正式首版交付范围：这个固定 x86 构建的后台键盘菜单通路、统一 MCP、安全生命周期和可回收加载。通过正式验收后才能更新生产支持声明。

## 2. 推荐方案与取舍

推荐新建低耦合的 `native_input` 后端，复用 Proto Input 的必要进程内 hook 和 EasyHook，增加受限动作执行与本项目的安全生命周期。首版仅编译 x86；x64 原型作为已有证据保留，不同时产品化。

采用显式按时间操作的协议 v2，v1 桥保持原有按游戏帧语义。共享上层工具名称及会话、暂停代次、结果查询和证据规则，按能力选择计时方式；不把输入查询次数、采集次数或时间乘以假定帧率写成游戏帧。

理由：原型证明了通用输入接口可用，没有证明可以控制真实游戏循环。若坚持完全沿用 v1 的游戏帧和冻结语义，就必须先为该游戏寻找循环钩子，会重新引入游戏专用适配。这条路线适合以后确有逐帧任务时单独评估。

不直接转用完整 Nucleus：其设备分配、实例管理及输入锁定方式与当前目标不同，且不能将 GPL 代码混入 MIT 来源的复用范围。不引入虚拟机、驱动或全局桌面输入。

本设计中的安全上限是拟定约束，不是已测性能数据；实施和验收不得为了通过而放宽。

## 3. 模块与启动入口

| 拟定位置 | 职责 |
|---|---|
| `plugins/native_input/prepare.py` | 检查样本和外部写入边界，准备新副本、会话、基线与恢复记录；拒绝覆盖已有目录 |
| `plugins/native_input/build.py` | 用已有 MSVC 构建 x86 宿主、DLL 和自有测试程序；输出到外置构建目录 |
| `plugins/native_input/Host.cpp` | 挂起创建、Job、引导期守卫、DLL 初始化顺序、启动与退出期限、进程树回收 |
| `plugins/native_input/Bridge.cpp` 及局部头文件 | 输入 hook、有界动作、安全状态、独立看门狗、协议 I/O 和截图结果发布 |
| `plugins/native_input/samples/` | 固定哈希、架构、数据标志、键位和被测输入路径；不按游戏名称猜兼容性 |
| `gameqakit/control.py`、`gameqakit/mcp_server.py` | 按协议版本和能力校验；同一组工具支持显式时间动作 |
| `gameqakit/engines.py` | 只读识别候选与固定档案匹配；识别结果仍不等于本次连接已就绪 |
| `tests/test_native_input_control.py`、`tests/native_input/` | 协议行为、原生输入、生命周期与真实入口验收 |

首版使用既有 `files-v1` JSON 文件封装与原子发布方式，协议版本与传输名分别校验：传输名不代表协议语义。不开另一套共享内存协议，也不导入 Wolf 插件作为运行依赖。

文件读写和截图不得发生在游戏输入回调或看门狗持锁区；I/O 工作线程发布内存快照，hook 只执行有界内存操作。一次最多一条在执行命令，不增加后台批量动作队列。文件系统卡住时允许安全失败，不允许阻塞释放。首版不承诺吞吐量改善，实测不足再决定传输优化。

准备入口明确列出源目录、E 盘副本、拟加载文件和已核查的保存路径；同意正式设计不等于授权向任意原游戏注入。只允许工具自己挂起创建的副本进程，不附加现有运行进程。生成物和运行数据全部位于 `<验证目录>`，本机按约定选在 E 盘专用目录。

## 4. 协议与能力契约

### 4.1 版本与兼容

- 现有 v1 请求、响应、`frame`、`after_frame`、`frames` 及 1–120 帧范围保持原义。
- 新后端使用 `protocol=2`；会话元数据、状态、命令和结果必须同版。未知版本拒绝，不能自动降成 v1。
- v2 的 `timing_mode=duration_ms`、`pause_scope=input`、`simulation_pause=false`；不提供 `frame`、`capture_frame` 或按帧单步能力。
- v2 使用 `observation_seq` 标识本会话发布的截图次序，命令携带 `after_observation_seq` 引用发送前已获得的画面。它不能证明游戏推进了几帧；引用未知、未来或其他会话的画面必须拒绝。
- `gameqakit/control.py` 的版本分派不得删除 v1 的 `frame` 检查。MV/MZ JavaScript、VX Ace Ruby 必须同步明确的版本／时间参数拒绝行为及回归；Unity、HSP、Wolf、DuckStation 的 v1 边界一并回归。不能只改 Python。

### 4.2 统一 MCP

沿用 `control_status`、`control_action`、`control_result`、`control_pause`、`control_resume`，不增加引擎专属动作工具。

拟定 `control_action` 增加可选 `duration_ms`，将 `frames` 的工具默认值改为未指定，再在版本校验后处理：

- v1 未给时长仍使用原来的 1 帧默认；显式传入 `duration_ms` 拒绝。
- v2 动作必须显式给 `duration_ms`；传入 `frames` 或同时给两种单位均拒绝，不隐式换算。
- v2 恢复是控制状态操作，不推进游戏、不需要时长；恢复成功仍须确认会话、暂停代次及新观察有效。
- v2 的 `move`、`confirm`、`cancel`、`wait` 使用整数 1–1000 毫秒；布尔值、浮点、未知字段、越界及未声明按钮拒绝。
- 首版不开放 `press`、`release`、`click`：动作执行器自己配对按下／松开，暂停与停止始终可清空全部输入。先把已验键盘范围做完整，再按独立验收增加鼠标和跨命令保持。

状态同时公开版本、计时／暂停语义、动作列表、时长上限、连接原因、输入后端、当前保持键、截图可用性与原生安全状态。调用端不能只根据 `adapter` 名称判定可用。

### 4.3 回执与消费证据

v2 结果至少包含会话、命令编号、暂停代次、`ok`、`consumed`、实际起止单调时间、按下／释放证据、结束保持键、截图序号／路径／摘要及错误原因。

- 编号由会话内单调序列生成，不使用毫秒时钟充当唯一编号。重复编号只能查询原结果，不能重放动作。
- 按键事件进入队列不等于被消费。固定 SRPG 样本以 `GetDeviceData` 实际移除对应事件为消费依据；`DIGDD_PEEK` 不算。状态式样本须有针对当前动作的查询证据。
- 动作期限到达先松键，再取得新的输入查询／释放证据，随后采集画面；超时不把“已经按过”算成功。`wait` 只表示无输入观察时段完成，不声称按键被游戏消费。
- `ok=true` 表示协议、释放和取图完成；实际菜单是否变化仍须读图。计数不增加、黑帧、陈旧截图、释放未知时返回失败并停止后续动作。
- 命令超时且结果未知时查询原编号，不自动重发确认／取消等可能重复生效的输入。

## 5. 输入与人工模式

首版拟声明的按钮只有方向、确认、取消；映射绑定样本档案，确认／取消使用已在原型路线验证的键位，不扩展任意虚拟键码。

DirectInput 状态与缓冲事件必须来自同一份逻辑状态，包含扩展扫描码、`DIGDD_PEEK`、事件序号、容量、设备释放／重建和非法调用参数测试。设备生命周期需正式处理，不能照搬原型按指针登记后永久保留的实现。输入队列有界；满载时先释放并失败，不丢弃松开事件继续运行。

AI 模式过滤目标进程内的实体键鼠，软件动作不走全局 `SendInput`。焦点、系统光标、捕获及 RawInput 路径按样本需要拦截；后台运行不足时拒绝连接，不激活窗口补救。游戏鼠标控制不开放也必须阻止实体鼠标串入。

`control_pause` 立即作废排队动作并清空软件输入，但仍保留实体输入隔离。暂停 AI 不是自动恢复实体设备通路，也不表示游戏画面被冻结。

人工手玩继续使用原有观察链，只采集和标记。首版不做运行中切换 hook 的新状态机：要从受控副本切到人工手玩，先停止并回收受控进程，再使用正常人工游戏及只观察模式；不得把 `control_pause` 描述成已完成运行中人工接管。不触碰老师原来的手测进程。若实际任务要求在同一进程保留进度并切换人工，则另行设计、批准和验证，不以偷偷透传实体输入替代。

## 6. 安全生命周期与数据边界

### 6.1 加载和写入守卫

顺序必须为：校验档案和副本边界 → 挂起创建 → 纳入 Job → 引导期限制 → 加载 DLL → 运行期守卫与输入隔离就绪 → 自检 → 恢复主线程 → 等待有效窗口及画面 → 发布可控状态。

- 只允许固定哈希及 x86。EXE 和实际加载 DLL 均记录摘要，加载前复核；检查根目录、重解析点和路径逃逸，不接受指向源目录的链接。
- 首版仅允许数据路径已核查的 `data.dts` 构建模式，缺标志或外部写入路径不明时停止准备。
- 引导期和运行期均保留副本外文件／注册表写入限制，不因游戏报错而关闭。复用语义应建立在带测试的局部实现上，不能通过绝对路径包含另一个插件。
- 明确保留 `\Device\KsecDD` 的既有系统加密设备例外，沿用自有加密程序的失败／恢复对照；这不是普通外部文件写入许可。
- 源目录及已核查外部保存位置记录前后摘要；保存记录、失败证据与副本差异归档后才回收可再生副本。首版不操作存档，不把副本变化同步回源目录。
- 不声称这是完整操作系统沙箱；网络、未知设备和未覆盖系统调用不由该守卫提供通用隔离保证。未核查样本不得通过改档案强行启动。

### 6.2 暂停、失联和期限

- 采用本项目已有的 1.5 秒租约与 3 秒截图期限，首次就绪期限为 15 秒；这是首版拟采用的硬上限，不是启动性能承诺。
- DLL 用单调时钟独立执行租约和动作期限检查；动作最长 1000 毫秒。主机不能无限自续租，续租绑定当前有效会话和正在处理的有限操作。
- 输入动作期间，目标输入通路连续 1 秒无查询则失败释放；输入查询次数只作通路健康依据，不能冒充逻辑帧或渲染心跳。
- 看门狗不能依赖窗口线程消息循环，不能与截图、文件操作或窗口回调共用长时间持有的锁。控制线程被阻塞时仍须释放；无法确认释放时宿主在有界期限内终止 Job。
- 暂停先发布新代次，再清空待执行命令、软件保持和未消费事件。旧代次不得续租或恢复；同时释放已被游戏读取的按键，并确认目标读取了释放状态／事件。接收请求后读取最新租约与暂停代次，避免把新请求与旧租约配对；用确定性交错测试验证，不能复现 Unity 旧读序竞态。
- 停止、主机崩溃、MCP 退出、窗口销毁和租约到期均进入释放／回收路径。重连创建新会话，不能沿用原代次和排队动作。

文件通道不是抵御当前用户恶意进程的安全边界。保留既有会话目录与目标身份校验，不将原型公开消息窗口、无会话操作码和窗口标题当作生产控制身份。

## 7. 截图和完成条件

复用项目已验证的窗口客户区取图方法，按实际窗口尺寸与 DPI 校验，不能保留原型硬编码画布。零尺寸创建阶段不发布就绪，尺寸稳定且首张有效图像通过后才允许输入。

- 截图采集不激活目标、不恢复最小化窗口、不移动系统鼠标。
- 每张图绑定会话、窗口／PID、命令、序号、采集时刻和摘要；不得复用旧图冒充动作后的观察。
- 新截图不等于像素必须不同：静止标题允许相同像素；通过按键移动光标等预期变化检查持续新画面，不能仅凭截图文件时间或计数宣称游戏仍在推进。
- 截图失败、无效画面或无法确认更新时停止、松键并记录。不得放宽黑帧判据，或退回抢前台操作。
- 最小化、GPU 后端、游戏鼠标和音频均须独立验证，首版不宣称支持。

## 8. 实施顺序与验收

批准后按下列顺序执行，每步先建立会因目标行为缺失而失败的测试，再最小实现。已有实验不重复当作生产验收。

| 顺序 | 工作与验收门槛 |
|---|---|
| 1 | 为 v1/v2 版本、时间单位、默认值、非法参数、状态和结果写行为测试；明确 v1 桥拒绝 v2／时间参数，保留按帧语义；引擎识别改动先在 `tests/test_engines.py` 跑红，再改实现 |
| 2 | 实现 x86 输入核心与有界队列；自有程序验证按下／松开、状态／缓冲一致、预读、队列满、设备重建、暂停和旧代次拒绝 |
| 3 | 实现宿主与写入限制；自有程序验证挂起／Job／守卫顺序、KsecDD、路径逃逸、外部文件／注册表拒绝、启动及卸载失败回收 |
| 4 | 故障注入验证 I/O／截图／窗口线程卡住、控制端突然退出、租约到期和释放确认超时；不得残留软件保持或孤儿进程 |
| 5 | 通过真实 MCP 调用自有窗口，核对状态、动作、结果、暂停／恢复和截图链，不以单独调用 DLL 代替入口验收 |
| 6 | 仅在固定游戏副本重放已验菜单路线；逐图确认标题切项、设置打开和取消返回；核对原目录及外部摘要、退出和回收 |
| 7 | 游戏侧实体键鼠并发单独验收：用户准备好才开始，在另一自有窗口操作；同时证明 AI 输入生效、人工侧无软件输入、游戏侧无人工输入和前台归属 |
| 8 | 运行受影响回归，归档证据；达到该级门槛才更新覆盖表、README、MCP 说明、插件开发规范及 CHANGES |

第 7 步需要用户实际输入，提前提供普通语言说明；不能用历史 x64 并发代替。若用户尚未参与，明确保持“游戏并发未验”，不得将完整目标标记完成。

回归命令沿用现有入口：

```bash
python -W error::ResourceWarning -m unittest discover -s tests -v
node --test tests/rpgmaker_bridge.test.js
```

原生构建采用既有 MSVC `/W4 /WX` 约定；正式新增测试入口在实现阶段提供。现有需要本机 fixture 的测试按原规则提供，不把跳过算通过。测试分组至少包含 `test_control`（含统一 MCP 用例）、`test_sessions`、`test_target_routing`、`test_engines`、Unity、HSP、Wolf 和 DuckStation；Ruby 桥没有独立现成自动化入口的部分，用自有 RGSS3 工程运行拒绝／原帧操作验证，不声称 Python 文本断言替代运行证据。

验收报告分开记录：协议回归、原生安全、自有并发、固定游戏菜单、固定游戏实体并发。附截图／摘要、每命令消费及释放记录、原数据摘要、记录 PID 退出和副本回收结果；失败批次单独保留。

## 9. 止损、回滚和发布边界

- 若 hook 仍会干扰用户输入、无法有界释放、需抢前台才能取图，或必须大量增加游戏专用逻辑才能完成已验菜单路线，停止正式接入，保留现有引擎桥和原型证据。
- 不通过延长期限、关闭保护、降低截图标准或拿回执替代画面完成验收。
- 新插件、构建和运行数据与既有后端分开；回滚停止并回收新进程，恢复主程序与桥的成套版本，创建新会话。旧文件不可与 v2 会话混用。
- 提交代码不包含原游戏、存档、编译二进制及本机证据。原型目录继续保留，不把失败证据当缓存删除。
- 只有正式自有／游戏验收通过后才启用该档案。未知构建保持拒绝，不能仅识别到 SRPG Studio 就自动加载。

Proto Input 和本机使用的 EasyHook 根许可证均已读取，均为 MIT；复用文件保留原声明，固定来源与摘要列入第三方清单。Nucleus GPL 实现不复制进入后端；其他传递依赖在进入正式源码时逐项核对。
