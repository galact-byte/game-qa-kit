# Wolf RPG 正式桥设计

状态：用户已批准按本方案实施；正式桥首版已完成自动回归、安全生命周期、真实 MCP 与地图操作验收。兼容范围仅限本文固定哈希的官方范例；实施与证据入口见 [实现计划](../plans/2026-11-10-wolf-control-plan.md)、[插件说明](../../../plugins/wolf/README.md) 和 `<Wolf验证目录>/正式桥验收.md`。

## 目标与依据

使当前 Wolf RPG 官方中文范例通过现有 MCP／`gameqakit/control.py` 接受正常游戏输入，动作后返回执行轮次、消费证据及新截图。人工盯屏入口照常保留。

已测范例为 Windows x86，EXE SHA-256：`90800e5dff9fa992a1fa78be5b2d5158baf2e9cc9603a45d964358e919f6868a`。项目外 `<Wolf验证目录>/帧边界验证.md` 与 `frame-01/verification.json` 保存探针结果和原始证据。仅声明这个构建，不推导其他 Wolf 版本或商业游戏兼容。

## 建议方案与取舍

维护者建议使用独立的 Windows x86 原生 DLL，放在 `plugins/wolf/`。项目已有 HSP／DuckStation 原生桥和 MSVC 构建方式；沿用既有协议语义，避免让正式控制依赖排障工具。

临时 Frida 脚本继续作为定位证据，不直接升级为长期运行入口。Frida 方案能较快复用探针，但会增加正式运行依赖和进程生命周期管理面；原生方案需补加载器与挂接安全检查。当前已有输入与完整循环实测依据，建议承担这部分一次性实现成本。

不扩展统一协议，不让 Wolf 插件导入其他引擎插件。只有识别模块和文档需要增加 Wolf 的可用实现声明。其他桥的源码和构建保持现有行为。

## 模块边界

- 便携准备入口：校验来源构建，拒绝覆盖原目录和已有输出，创建测试副本与还原清单。准备与加载两端均检查完整 EXE 哈希，不能只看版本字符串。
- 加载入口：只面向本次创建、绑定独立桌面和 Job Object 的 x86 测试进程。按实际模块基址计算地址，核对调用点字节与目标后再挂接；初始化不完整即拒绝输入。跨位数加载需要随桥构建的 x86 辅助程序，不依赖系统级键鼠输入。
- 安全核心：独立于 Win32 和游戏挂接，可用受控时间与轮次编译测试。维护会话、暂停代次、租约、动作、结果去重及帧推进状态。
- 运行桥：在游戏线程的主循环边界调度动作，覆盖当前键盘设备的正常 DirectInput 状态，发布既有 INI／JSON 协议与截图。工作线程仅接收／发布文件及维护心跳，不在其他线程直接执行游戏逻辑。
- 识别与客户端：识别 Wolf 并绑定现有 `command_format=ini`；使用现有能力协商。不支持的动作必须拒绝。

## 执行与计帧

已实测主循环顺序为输入处理、游戏逻辑、更新绘制、循环尾部。主循环输入调用返回点为 `0x4ec857`；逻辑、绘制和尾部的调用返回点分别为 `0x4ec8e1`、`0x4ec8f5`、`0x4ec8fc`。这些是已测映像的静态虚拟地址，挂接前须换算基址、验证字节；不能直接套用于其他构建。

输入轮询同一轮可出现多次。12 轮位移和松键观察分别有 87、68 次输入轮询，因此计帧只取完整完成的游戏循环。状态与文档称为游戏更新轮次，不承诺固定墙钟帧率或一次物理显示刷新。

初始状态暂停、输入归零。显式恢复后，方向／确认／取消／按键保持在请求的完整轮次内生效；到期释放，再按既有动作后观察语义获取新图。请求轮次与释放后观察轮次分别记录，不把观察轮次算成长按。

首版只开放经过设备读取和实际画面验证的键盘能力，帧数遵循现有客户端限制。鼠标点击、实体手柄及未验证按钮不声明为可用。菜单刚打开时一轮输入可能未被游戏消费，必须如实记录，不能用注入成功代替画面变化。

## 安全与结果语义

- 精确绑定 `session_id`、PID、EXE 路径和独立桌面；其他会话、旧暂停代次和重复请求不能推进动作。
- 先取待处理请求，再读取租约／暂停信息，避免把新请求与旧租约配对；读文件失败不延长租约。
- 优先暂停和租约过期释放全部合成按键，停止后续游戏更新；暂停期间保持心跳和命令查询可用。
- 同一 `command_id` 查询不重发；迟到成功与失败终态分别保留。超时后必须显式恢复，不能自动补发按键。
- 操作后截图必须在动作完成后获取，通过现有 PNG／路径检查并原子发布。截图失败、停更、计帧异常或输入未被消费时停止；不能回退系统输入或抢前台。
- 设备读取次数只作消费辅助证据。可用性验收还必须看真实标题切项、地图位移与菜单变化。
- 执行等待与截图处理分别计时，使用既有协议的时限和失败语义，不为跑通而放宽租约、心跳、客户端超时或截图规则。
- 不把“线程卡住时保证游戏内代码立即响应暂停”作为未验证承诺；无法确认停止时由宿主报告失联并结束本次自有进程树。

## 数据范围与还原

全部生成物与运行数据落在 E 盘专用验证目录，原游戏目录保持只读。本次范例已发现相对游戏目录的 `Save/SaveData`、`Game.ini` 与 `debug.log`；商业样本仍须单独静态核查，不把独立桌面当文件系统沙箱。

验证使用全新副本，不带入老师的游戏存档，不保存测试进度。启动前记录来源完整文件清单与哈希；运行后再次核对原目录。测试副本改写前保存原件，副本变化与失败批次分别归档。退出自有进程使进程内挂接随之结束，再回收 runtime 即为还原，不向原目录回写。

探针中的外部写入拦截属于探针措施，不能把它省略后仍宣称同等数据隔离。正式范例运行前重新核对写入边界；若发现超出副本的持久化写入，先处理这一阻碍再扩大测试。

## 验收条件

正式桥完成须同时满足以下证据，探针结果不能替代：

1. 安全核心测试先红后绿，覆盖精确完整轮次、重复输入轮询不增帧、按住到期释放、暂停、租约过期、重复命令、旧会话／代次、帧回退、未消费和截图失败。
2. 准备与加载入口拒绝不同哈希、错误位数、错误进程绑定和不匹配调用点；失败不产生已连接假象。
3. 使用现有 MCP 真实子进程，验证初始暂停、恢复、标题切项与确认入图；地图定帧位移、松键停止、菜单打开／切项／关闭均逐图核对。
4. 实机验证运行中暂停、租约到期释放，暂停期间完整循环不增加；按原编号查询不重发，失败后只能显式恢复。包含截图失败停止和恢复的新图证据。
5. 原目录完整哈希零差异，失败批次原样保留，最终证据清单核对，所有自有进程与运行副本回收；文档只声明正式桥实际验过的范围。
6. 受影响 Python／C++ 测试、既有 JavaScript 回归和差异检查通过。仅在统一协议确需变动时重新审查跨桥同步范围，本方案不安排该变动。
