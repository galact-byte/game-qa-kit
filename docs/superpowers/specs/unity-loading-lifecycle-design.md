# Unity 加载期心跳与受管回收：待审阅设计

状态：第一阶段耗时诊断已获批并完成实现与空白场景验证；生命周期策略仍待审阅。现行 2 秒心跳、15 秒启动期限、黑帧判据、松键确认及失败回收保持不变。

## 问题与事实更正

Rewired 固定构建的新游戏和读档入图，以及 IL2CPP 固定构建的第三批，均在加载期间触发现行心跳保护，正式受管整链未通过。

此前将 IL2CPP 第三批表述为“停在 Loading”不够准确：最后一次动作截图与当步 Qt 对应观察图确实是 Loading，但回收后保全的最终 `status.json` 已为 `ConversationScene`，最终 `screenshots/startup.png` 可见剧情人物、对白框及“您好，你就是这次被分配来的见习生莉莉亚吧？”的对白。它证明回收前曾呈现剧情画面，不证明失联瞬间已经完成加载，也不证明后续输入、Qt 同步或松键成功。第二批与第三批均留存剧情图，但第二批因验收驱动判图窗口结束而未完成后续动作；第三批为心跳故障，`release_confirmed=false`。两者均不计完整通过。

原始材料仅保留本地：`<接入验证目录>/real-unity-il2cpp-managed-{02,03}/` 下的 `audit.json`、`step-02.png`、`current-step-02.png`（第三批）、`session/bridge/status.json`、`session/bridge/screenshots/startup.png`、`session/cleanup.json`。只读核对脚本与摘要清单为 `<接入验证目录>/validation/verify_unity_loading_evidence.py`、`unity-loading-evidence.json`。

## 已查清的调用关系

- `plugins/unity/GameQaBridge.cs` 的 `Update()` 调用 `Tick()`，`Tick()` 处理命令、租约、暂停、输入后端，并发布状态。
- `WriteStatus()` 在主线程调用 `View()` 查询场景、根对象、UI 等内容；发布间隔为 0.2 秒。当前 `updated_at` 在构造状态时取得，后续 `View()` 耗时不单独记录。
- 调查基线中的帧末截图同样依赖主线程，使用 `ReadPixels`、PNG 编码及文件写入；被动观察间隔为 0.5 秒。第一阶段诊断现已分别记录这些阶段耗时。
- `gameqakit/control.py` 校验真实会话、PID 和路径后，要求心跳年龄处于现行 `[-1, 2]` 秒范围；过期即拒绝控制。
- `gameqakit/game_worker.py` 的运行期轮询把失联视为终止条件，进入 `UnitySession.stop()`。
- `plugins/unity/session.py` 在桥仍连接时发布暂停并等待最多 3 秒确认；若初次状态已失联，则记录松键失败并回收自有目标，不等待桥恢复。

因此，主线程加载、状态遍历、截图或文件操作阻塞都可能表现为同一种心跳断档。现有归档不能唯一地区分它们，也没有记录故障触发时的完整状态及单调时钟时间线。不能把 `DressController` 的错误日志、最终剧情图、文件修改时间或进程仍存在分别当作根因或安全恢复证明。

## 目标与边界

目标是在不让失效输入继续执行、不把旧图充当新图、不伪造松键确认的前提下，区分加载中的暂时停顿与无法恢复的故障。是否允许加载期间延后进程回收，是本设计需要老师决定的架构边界。

不改变游戏场景逻辑，不直接调用读档、任务完成或切场景；测试仍由正常键鼠动作触发。仅使用已经核查保存边界的 E 盘副本，独立桌面运行；原目录、原保存数据与 PlayerPrefs 持续按前后摘要核对。

## 三种方案与推荐

| 方案 | 收益 | 代价与限制 | 决策 |
| --- | --- | --- | --- |
| 保持现状并补诊断 | 不改变安全行为，可定位耗时阶段 | 当前加载阻碍继续存在 | 所有后续变更之前必须先执行的取证步骤 |
| 单纯延长心跳，或另开线程更新时间戳 | 改动看似小 | 不能证明主线程处理输入、生成新图或读取松键；会混淆存活与可控制 | 不采用 |
| 将控制新鲜度与加载期有界观察分开 | 保留 2 秒控制停手条件，可在满足额外条件时观察加载是否恢复 | 改变故障回收时机，必须新增状态、明确期限与释放证明；需要审批和实测 | 推荐的架构方向，待批准 |

推荐分开两种证据：主线程控制／画面新鲜度继续决定能否发输入；诊断线程或宿主存活证据只帮助定位，绝不把失效主线程重新标为可控制。

## 推荐方向的状态与失败语义

1. `ready_paused`／控制阶段维持现行规则。心跳过期、画面停更或截图错误立即禁止后续游戏输入，取消尚未执行的命令；不自动重放故障前的动作。
2. 拟新增的加载观察状态必须显示“禁止控制，等待加载核对”。只有能够证明进入了明确加载生命周期、且有目标确认读取到松键的记录时，才讨论允许该状态延后回收。未确认松键、未知停顿、身份变化、目标退出、取消或图像错误继续走原失败回收。
3. 加载期间只观察，不把动作消费回执或旧截图当作新进度。独立存活信号不能修改 `frame`、`input_ready`、`held`、松键确认或画面序号。
4. 恢复必须同时看到新的主线程状态、有效新图、同一会话身份和目标确认松键。恢复后保持暂停，原失败动作保留为失败，重新控制需显式恢复；不得在失联后自动续跑队列。
5. 达到固定加载观察期限则终止；期限不因重复 Loading 图、后台存活脉冲或状态查询而续期。人工暂停／取消有独立确认路径，不等待加载期限耗尽。
6. 无论最后是否出现剧情，都按实际回执记录 `release_confirmed`。未经确认的松键不能追认，失败批次不能改记通过。

**可行性门槛：目前尚未证明这两个固定构建能在耗时加载开始前完成目标侧松键确认。** 若加载由同一帧的点击直接触发，且目标来不及读取松开，则上述加载观察入口不可启用，仍按现行回收。不能为了支持样本而取消此门槛。

## 先取证，再确定实现范围

第一阶段只增加限量诊断，不改控制授权、期限或回收策略：

- 在桥中用单调时钟记录 `Tick`、输入后端、`View`、帧末取图、PNG 编码及文件发布的耗时；记录最近阶段、最后完成帧和观察序号。后台诊断仅读取不可变快照，禁止调用 Unity API 或发布控制心跳。
- 宿主在首次失联时保全读到的原始状态、心跳年龄、当前请求 ID、租约／暂停代次及单调时钟时间；错误记录失败也不能延后或阻止原回收。
- 诊断采用有界存储，默认关闭；采样和写入上限在实现审阅时明确，先测启用与关闭的开销。无证据前不预填“足够”的加载宽限秒数。
- 先在自有小样本注入主线程停顿、状态查询变慢及截图变慢，验证阶段区分与原失败回收。再决定是否值得重建一次商业完整副本，避免重复复制 12.46 GiB 却仍缺少关键时间线。

第二阶段只有在架构方向获批、第一阶段拿到耗时与松键顺序证据后，才确定加载观察入口、固定上限与是否需要修改控制协议。若实测不能满足松键门槛，保留阻碍并另行审阅方案。

## TDD 与验收顺序

1. 先固定现行边界：心跳年龄 1.999／2.000 秒可连接，2.001 秒拒绝；输入租约、优先暂停与帧末取图的生产代码测试保持通过。
2. 诊断 RED：可控的主线程停顿／慢 `View`／慢截图必须产生可区分且有界的记录；诊断写入失败不改变原失败路径；关闭诊断不创建资源；退出无残留诊断线程或打开文件。
3. 诊断 GREEN：最小实现，验证没有新心跳、没有自动输入、没有更晚的回收；测量额外写盘和耗时。
4. 若进入生命周期实现，先写 RED 覆盖：未知停顿、加载信号缺失、未确认松键、跨会话状态、旧图、超时、取消、重复恢复及后台脉冲伪装；任何一项不得恢复控制。
5. 生命周期 GREEN 后，在自有小样本执行正常加载与故障加载。只在方案满足门槛后重跑 Rewired／IL2CPP 商业副本的正常输入、实际画面变化、Qt 当前预览、松键、退出及三类原数据核对。
6. 全量受影响回归与文档一致性通过后才提交已完成块；未通过的后端继续披露限制。

若修改 `gameqakit/control.py` 的协议语义，必须同步 MV/MZ JavaScript、VX Ace RGSS3 桥及其测试；不能只给 Unity 加旁路。若仅增加 Unity 内部诊断且不改协议，则不扩展其他引擎实现。

## 审阅决定

请审阅的核心决定是：是否接受“2 秒仍立即禁止输入；只有可证明已松键的明确加载阶段，才允许独立且有固定上限的被动观察”这一架构方向。

批准该方向不等于批准任意延长心跳或预先批准加载上限。尚未测得的数值不写成保证；无法满足入口门槛时不落地等待状态。所有当前失败结论与保护规则在新证据及对应审批到位前保持。
