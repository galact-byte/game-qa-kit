# KiriKiri 固定构建 TJS 实验桥设计

日期：2026-11-16。状态：**待审，未批准实现**。

## 目的与范围

将已验证的固定 KiriKiri 2.32.2.426／x86 自写工程探针推进为统一 v2 毫秒协议的实验桥。首版仅支持 `confirm` 与 `wait`，保持候选识别的 `adapter=null`、`control_verified=false`。不接入产品启动界面，不加载商业资源、原存档或第三方游戏插件。

运行时必须完整匹配 SHA-256 `8db00ce0cd63748296d4e13b6916a4f1b5b166078f806d731202d15b210efe11`；版本号相同不能代替摘要验证。运行时不随源码分发。

## 已有证据与必要改变

1. 三组自写路径探针正常退出：默认数据目录位于副本 `savedata`；命令行 `-datapath` 覆盖 `.cf`；从已选目录读取的 `.cfu` 能改变后续参数查询，但没有重定位已经初始化的 `System.dataPath`。只代表本固定构建和探针，不是任意商业写入隔离。
2. 内嵌选项读取从 `XOPT_EMBED_AREA_ + 20` 开始，该处首字节为零。不能从后方残留的 `datapath` 字符串推断命令行会被过滤。路径实测也未支持此前的阻碍判断。
3. 原生 `Window.postInputEvent` 在独立桌面触发自写 Window 的正常 Enter 按下和松开处理器；前后图片从紫色等待画面变为绿色松键画面。
4. 在正常按下处理器中，原生单参数 `System.getKeyState(13)` 仍返回零；松开处理器也为零。原 KAG 脚本会调用同一查询，因此仅有事件投递不足以兼容这条输入通路。
5. 以上不是正式协议、安全生命周期、正常存读档或商业游戏验收。

原始证据见 `<KiriKiri验证目录>/path-probe-03/`、`input-probe-05/`；详细边界见[核查记录](../../KIRIKIRI-STATIC-REVIEW.md)。

## 推荐方案

采用独立 Python／Job 宿主与目标内 TJS 输入桥，在自写工程明确加载桥文件并显式绑定唯一测试 Window。继续使用原生 `postInputEvent` 触发原处理器，同时给 `System.getKeyState` 增加仅针对合成 Enter 的状态覆层。

这是建议的架构选择，尚未获得老师批准；不把临时探针直接转成正式插件。

- 相比只投递事件：状态覆层解决已观察到的原生查询始终为零的问题。
- 相比新增原生 DLL／进程注入：首版先利用已有脚本入口，不增加本机构建或钩子依赖；若 TJS 接口不允许覆写，停止并提交新证据，不自动转成 DLL 方案。
- 首版明确加载自写桥，不修改 EXE、不打补丁 XP3、不替换商业启动脚本。以后引入通用加载器或商业补丁须另审。

## 组件与职责

拟新增 `plugins/kirikiri/host.py`、`GameQaBridge.tjs`、`capture_worker.py`、`README.md` 与 `SOURCES.md`，以及 `tests/test_kirikiri_bridge.py` 和纯自写夹具。

- Python 宿主复用现有 `DesktopProcess`、v2 控制接口与取图函数，持有进程树和租约／活性期限，发布标准状态、回执与 PNG 摘要。
- TJS 桥在游戏线程读取有限的输入指令，维护合成 Enter 状态，通过目标 Window 的正常原生事件队列发送按下和松开。
- 捕获工作进程独立绑定目标桌面，复用 `gameqakit.win32.capture` 的客户区与黑白帧判定。正式插件不依赖 Emuera 或其他引擎插件。
- 自写夹具保留正常 Window 输入处理器；桥不直接改变场景、完成任务、修改进度或调用存读档结果函数。

宿主与 TJS 的内部文件采用有大小上限、白名单字段和完整序号首尾标记的 ASCII 记录；不对控制文件使用 `Scripts.eval`／`execStorage`／`Dictionary.loadStruct`。宿主负责标准 JSON 协议。缺失、截断、未知字段、非整数、越界时长、身份不符或序号倒退一律拒绝，不从半条记录执行输入。TJS 输出同样有完整记录标记，宿主只接受已完成记录；宿主的标准协议文件沿用原子发布。

## 状态查询与消费确认

1. 先验证 `System.getKeyState` 是否允许按预期包装、原 Window 方法能否绑定原上下文；这两项是实现前期的真实运行门槛，当前未验。
2. 保留原生查询函数；仅会话处于 AI 控制状态且键为 Enter 时，查询返回合成保持值，其他键沿用原函数。
3. 投递按下前设置合成保持值；在目标原处理器返回后记录按下分发已完成，以及原处理器确实查询到按下。正常处理器中的查询计数与画面变化共同作证，不以桥自己查询替代游戏消费。
4. 投递松开前清除合成保持值；同样等待原处理器返回及目标查询到松开。原处理器抛错时保留已经发生的消费阶段，暂停并释放，不报告成功。
5. 处理器返回不能独自证明任意游戏都消费了输入；初版只验明确可观测的自写 Window。目标重写方法、转交异步处理或绕过查询覆层时拒绝扩大兼容结论。
6. 松键未确认时不能只清空软件映射便认定释放成功；按独立释放期限终止本批 Job。
7. 暂停、错误或退出都清除保持状态；解除绑定时仅在方法仍由本桥持有时还原，不能覆盖目标后续修改。

## 协议、时间与故障规则

复用现有 v2：输入以 `duration_ms` 表示，1–1000 毫秒；不接受 `frames`，不把 Timer 次数称为游戏帧。初始暂停，首图通过后才允许显式恢复。输入暂停不承诺仿真暂停。

身份绑定包括协议、引擎、固定运行时摘要、PID、会话、目录与请求编号。重复请求只查询原结果，不重复执行；未知结果先查原编号。旧会话、历史观察与迟到回执不触发动作。

保留现有同类实验桥保护值：15 秒启动、1.5 秒租约、1 秒 UI 活性、1 秒目标释放确认、3 秒截图、1 秒正常关闭；宿主可控的短时共享冲突重试上限 100 毫秒。首次释放期限不因重复暂停或持续读错重新开始。目标内文件 I/O 可能阻塞时，由独立宿主依据活性／释放期限回收，不能靠阻塞线程自救。

首图沿用现有 99.9% 黑白帧判据，失败即零输入。后续取图或发布失败保留已发生的消费事实并停止新动作。停止、租约失效与人工暂停优先于队列。正常关闭先确认松键，再让自写工程正常退出，超期由 Job 兜底。

## 保存、回滚与来源

所有测试副本与生成物位于专用验证目录。只复制摘要匹配的 EXE 和自写 TJS；不携带原 `.cf`／`.cfu`、商业 XP3、MTool 或原保存数据。显式指定本批数据目录，核对 `System.dataPath`、环境配置、日志与生成文件落点。

存读档用夹具正常 Enter 菜单触发保存与读取，验证同进程与新会话恢复；桥会话和输入状态不得进入游戏存档。写入账本记录具体槽／文件、改前是否存在、备份和还原方式，不使用老师的保留槽。

原 EXE 与六份原存档执行前后逐一核对 SHA-256。独立桌面与目录定向不构成文件系统、注册表或网络沙箱，不扩大到商业任意脚本。

上游运行时完整许可与源码 revision 尚未核实。来源声明列出固定摘要、使用到的官方接口文档及许可缺口；只分发自有桥、测试与说明，不分发 EXE、商业内容、存档或反编译输出。撤回新增桥和记录即可回退，无原数据迁移。

## 验证与验收

按测试先行实现；各用例必须先因缺失行为失败，再由最小实现转绿。真实固定运行时验收至少包括：

- 摘要不符、身份错误、非法／截断记录、未恢复时动作拒绝；首张纯黑／白图零输入。
- 原处理器按下／松开、查询状态一致、操作后画面变化；重复编号不重复动作。
- 暂停后仍有新观察，人工暂停优先于排队动作，释放必须由目标确认。
- 租约失效、UI 卡死、截图工作进程卡死、发布失败、持续读错、重复暂停叠加未确认释放和长按退出均按原期限回收。
- 同进程与跨进程正常存读档；回执、画面、摘要、原文件、前台 HWND 前后与测试进程退出逐一核对。
- 缺运行时的测试明确跳过，不能把跳过写成实机通过。运行受影响测试和相关回归；只在共用协议实际变化时才扩大到全部家族桥，首版设计不需要修改共用协议。

没有可调用的独立审查代理，本文由执行者按实现者视角自查，不记为独立审查通过。老师批准本设计后，才编写实施计划并实现正式桥；当前仅交付探针证据、文档与待审设计。
