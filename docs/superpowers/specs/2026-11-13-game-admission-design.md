# 通用游戏接入入口设计

状态：方向已获用户授权；本文件为待审阅设计，尚未批准实施。本文中的模块、字段与工具名称均为提案，不代表当前程序已经提供。

用户已明确：真人／实体输入体验验收统一留到全部工作最后集中完成。该项未验不得阻塞可独立推进的实现和自动验证；自动验证也不能冒充真人通过。

## 1. 目标与非目标

让用户从现有 game-qa-kit 主程序选择游戏，由程序说明当前能做什么、缺什么，并在满足既有安全条件时准备、启动和连接受控副本。不要求普通用户编辑 JSON、拼接启动命令或按引擎寻找不同测试脚本。

主界面和现有 MCP 保留，人工盯屏继续是独立可用的正常入口。统一的是接入流程与会话生命周期，不是引擎插件，也不是把所有游戏变成通用后台游戏。

本轮不做：

- 新引擎、新输入协议、任意游戏注入、任意版本放行。
- 自动下载／安装运行时、加载器、模型、驱动或虚拟机。
- 自动导入原存档、存档修改、游戏玩法自动执行或同进程无缝人工接管。
- 通过普通窗口消息、全局键鼠、抢前台、放宽超时或降低判图标准兜底。
- 重做现有界面、替换 PyQt6、另造一个网页控制台或复制观察／证据链。

## 2. 推荐范围与取舍

推荐：增加薄接入层，调用既有引擎识别、适配器准备入口、BridgeClient 和观察链；按适配器逐项注册安全的启动流程。

不推荐直接包装 `tests/*_smoke.py` 作为产品启动器：这些脚本混合了构造测试数据、自动操作、断言和回收，启动成功可能立即进入预定动作或退出，生命周期与日常使用不同。也不推荐一次重写所有适配器，避免把未统一的保存边界藏在“支持该引擎”标签后。

建议分成可独立验证的交付块：

1. **通用核心**：只读检查、人工观察建配置、会话状态和已有受控会话的显式连接。
2. **首个完整启动流程**：只接已有固定 SRPG Studio x86 档案，复用正式 prepare 与 native-host。覆盖选择源游戏、准备新副本、有效首图、暂停就绪、显式控制、停止与证据回收。
3. **其余已有后端迁入**：Wolf、DuckStation、HSP、RPG Maker 与 Unity 分开接入；每个后端先补齐产品化准备和生命周期，再启用对应启动按钮。各自可独立迁入，不等待集中真人验收。

第 1 块不是只交一份 CLI 或要求用户手写配置，第 2 块也不冒称“全部引擎一键启动”。尚未迁入的后端仍保留原入口及已有控制能力。

上述分块为本设计的工程建议，并非用户要求只支持原生后端；审批时需一并审阅这一交付边界。

| [profile.py](../../../gameqakit/profile.py) | 精确 exe_path 可持久化，target_pid 仅限当前运行态；新入口不得把历史 PID 当有效目标 |

| [native_input/prepare.py](../../../plugins/native_input/prepare.py) | 固定 EXE、资源、后台配置、重解析点及目录边界检查；新副本、不带原 Save、原目录及外部数据基线 |

| [hsp/prepare.py](../../../plugins/hsp/prepare.py) | 仅向外置字节码追加插件注册，不负责完整游戏副本、运行时发现及保存隔离 |

源码核对不等于新增运行验证。真实控制覆盖仍以[引擎覆盖表](../../ENGINE-COVERAGE.md)为准。

## 4. 用户流程

### 4.1 人工观察

选择已运行的游戏窗口，自动读取 PID、精确程序路径及可用尺寸，生成普通 profile；只观察、留图与标记。不向该进程加载插件、不停止用户游戏，也不因选择“人工”就发送任何键鼠。

未运行的目录可先只读识别；未知游戏不能由工具擅自启动原 EXE。用户正常打开游戏后，再由进程选择入口绑定。无法确定的保存路径保持未设置，相关改档功能继续不可用。

### 4.2 AI 后台接入

1. 选择游戏 EXE 或目录，检查仅针对所选目录，不默认扫描整盘。
2. 显示引擎证据、可用后端、构建／依赖、保存边界和“本次接入”的阻碍。未知引擎、未匹配构建、只有已验插件但没有安全启动流程必须区别显示。
3. 条件成立后展示一次本次操作摘要：原目录只读、新副本位置、将加载的本机产物、保护范围、不带原存档、预计占用的可测部分及回收方式。确认只覆盖这份摘要，不扩大为其他目录或后端授权。
4. 准备副本；按后端规定启动；验证当前会话身份和首图。初始为**暂停就绪**，不能因为点击“启动”自动执行菜单路线或恢复 AI 输入。
5. AI 通过现有统一控制工具明确恢复和发动作。每次动作沿用原协议、消费、释放和新截图检查。
6. 停止后释放、退出自有进程、核对数据基线并归档；只在清楚的数据处置规则下回收本次可再生文件。

检查失败应给出普通语言原因和下一步，不把底层参数、Python 堆栈或手写配置作为用户唯一恢复手段。已知加载器缺失时允许选择已有安装／构建目录，不提供静默安装。

### 4.3 连接已有受控会话

可以从用户选择的 QA 会话父目录列出有界数量的接入记录；不全盘搜索进程或桥目录。连接本身不附加或注入进程、不接管所有权、不恢复输入。

现有测试会话只有 connection.json 不足以自动认定为“本工具可停止的会话”。用户可选择桥目录查询并绑定当前身份，但必须保留“外部管理、不能代为回收”的区别；不伪造受管记录来绕过启动边界。

## 5. 检查与会话数据

接入检查建议返回以下概念，而不是只返回一个 supported 布尔值：

- 只读引擎结果及证据。
- 后端候选和确切样本／构建匹配结果。
- `launch_readiness`：可准备、已识别但未迁入、缺本机产物、保存边界未核查、未知／不匹配。
- 每条阻碍的稳定错误码、用户可读说明、对应字段和可行恢复动作。
- 版本化准备摘要及摘要指纹：源路径、EXE、关键配置、后端、产物、目标目录与数据处置规则。
- 自动验证、真人验收、实际能力三个维度分开记录；识别成功不改变 control_verified。

本机依赖登记只保存路径、版本／摘要和已知选项，不允许外部登记任意可执行命令、Python 模块、shell 片段或下载地址。后端映射由仓库代码明确注册，不做动态插件市场或宽泛配置 DSL。

启动前重验已确认摘要：源 EXE、关键配置、产物和目标目录改变时原确认失效，不能静默换 DLL 或继续旧计划。读取源数据到复制之间的变化通过复制摘要和启动端复验继续防护，不能以一次预检代替所有校验。

每个受管会话新建独立目录，包含：

- 准备摘要、来源与本次授权记录、只读基线和恢复账本。
- 版本化 session.json：后端、启动者、当前目标身份、bridge 位置、进程所有权与状态；不是控制协议的替代品。
- 标准 GameProfile、桥文件、原始观察／动作证据及日志。
- 副本准备和收尾结果；失败记录保留，不能覆盖成功或历史失败。

PID 只在运行记录中出现；重新连接必须核对实际 PID 路径、会话与心跳。未验证或已退出的连接不能靠 profile 名字复活。

所有新产物位于用户明确选择的 QA 数据根目录，本机沿用既有非系统盘约定。首次选择一次即可记住，不隐式回退到用户主目录或系统临时目录；登记的依赖路径与新入口设置也保存在该根目录。源目录、存档、父子目录重叠、已存在目标及符号链接／junction 拒绝。旧 profile 与既有数据不迁移、不覆盖；新 profile 名冲突时生成新标识。

## 6. 模块与接口边界

以下均为拟定位置，不是已实现 API。

| 位置 | 职责 |
|---|---|
| `gameqakit/admission.py` | 只读检查、有限后端注册、准备摘要和状态分类；不创建进程、不发输入 |
| `gameqakit/game_session.py` | 一份受管会话的准备／启动／连接／停止编排、锁、身份及证据；GUI、CLI、MCP 共用 |
| `gameqakit/game_worker.py` | 有界后台准备和生命周期任务；与 UI 线程分开，不执行游戏测试脚本 |
| `gameqakit/process_job.py` | 从现有桌面封装提取最小的挂起／Job 自有进程能力；桌面可选但不得默认给已有后端换桌面 |
| `plugins/<backend>/session.py` | 在各自插件内复用既有准备与加载流程；不互相导入，避免在 GUI 堆引擎判断 |
| `gameqakit/gui.py` | 复用原主程序，增加接入与运行状态；旧人工盯屏及高级 profile 编辑保留 |
| `gameqakit/mcp_server.py`、`gameqakit/cli.py` | 仅暴露共用接入操作，继续调用既有 control_* 执行游戏动作 |

先落地 admission 和会话编排所需的最小接口，不提前创建所有后端的空实现或抽象类。现有源码有可用的实现就复用；只有生命周期确有差异才留后端钩子。

拟定后台会话状态：

`checking → blocked / awaiting_confirmation → preparing → prepared → starting → ready_paused → stopping → stopped / cleanup_failed`

运行时另记录已确认的控制模式；`ready_paused` 必须来自 connected=true、有效首图、真实 paused=true、held=[]，不是异常回退得到的 paused=true。显式恢复后，状态来源仍为 BridgeClient；不维护一套与插件脱节的输入状态机。

不把原有手动 profile 强制改成受管会话。新版元数据使用显式版本，旧数据通过旧入口继续可用。

## 7. 启动者、退出和进程所有权

首个 native_input 流程调用其正式 prepare 和 native-host，不附加老师已经打开的游戏。原生后端仍在当前桌面；独立桌面后端仍由各自已验方式设置环境与连接，然后才恢复线程。

接入层需要真正的拥有者收尾，而不只是 GUI finally。首版采用有存续期的创建者进程（GUI、常驻 stdio MCP 或前台 CLI）和独立 worker 进程，不做脱离创建者继续运行的后台服务：

- 创建者独占外层 Job 的不可继承句柄，挂起创建 worker、入 Job 后再恢复；worker 再独占本次宿主 Job 的不可继承句柄，挂起创建宿主、入 Job 后再恢复。游戏子进程仍受 native-host 内部 Job／守卫约束。各层不向子进程或连接者复制 Job 句柄，也不允许 breakaway；否则最后句柄关闭时回收的保证不成立。
- GUI 关闭时先请求 worker 正常停止，再关闭外层 Job 并等待自有树退出；GUI／MCP 创建者意外退出时外层句柄关闭回收 worker 及其后代。worker 意外退出时其宿主 Job 句柄关闭，宿主／目标不得继续运行。CLI 启动受管游戏必须保持前台生命周期，退出即收尾，不以打印 session_id 后退出实现分离运行。
- native-host 现有内部 Job／守卫继续保留。新增外层拥有关系必须用真实 Windows 故障测试验证完整嵌套链；任一分配失败都在恢复线程前终止已创建进程并拒绝启动，不允许无 Job 继续。原有独立桌面后端的桌面归属不因此改变。
- 只有创建者可以经自己持有的 worker 通道和进程句柄停止、回收本批进程。首版不增加跨创建者的停止 RPC；连接者只获得桥连接，不因 bind、断开或退出而得到进程所有权。状态明确返回是否可停止及应在哪个创建者窗口结束；其他 GUI／MCP 的停止请求明确拒绝，仍可按既有桥请求输入暂停。
- session.json 只提供发现与诊断，不赋予进程所有权；不能仅凭记录中的 PID、路径或同名进程执行终止。创建者崩溃后的记录标为中断／待核查，重启后不得自动收养或重启旧目标。确认旧树退出后可只读核对基线和保留数据；不能确定时保留现场并阻止自动回收。
- 新入口首版不提供“关闭控制台但保持 AI 自主运行”的守护模式，不引入服务或无限续租。

暂停不等于退出。按原后端的有限释放确认收尾；失败必须记录未确认状态，再按原 Job 回收，不延长期限、不对未知目标按名字 kill。复制取消发生在工具创建的新目录内，待当前有界步骤退出后归档；不会把用户提供的目录整体当缓存删除。

运行副本内以后可能产生用户希望保留的进度，因此普通结束不能默认递归删除整个会话。准备前的数据处置必须明确：初版自动路线只用无存档菜单会话；后端按已核查清单识别可再生变化，只有未产生新用户数据时才按记录回收 runtime。保存类或无法解释的变化一律保留并提示，不按通用文件名猜测、静默覆盖、同步或删除。失败证据、截图和基线永不跟随 runtime 回收而删除。

## 8. MCP 连接与观察链

不能用改写某个全局 active.json 让所有正在运行的 MCP 悄悄换目标，也不能以 GUI 切换游戏等同于另一 MCP 进程已重新绑定。

建议增加引擎无关的生命周期工具（名称待实现阶段最终核对）：`game_prepare`、`game_start`、`game_status`、`game_bind`、`game_unbind`、`game_stop`；只读引擎检查继续复用 `engine_inspect`。不增加 `native_move`、`unity_move` 等动作工具。

- prepare/start 明确授权具体准备摘要与受管会话；status 只读，不依赖已经存在的活动 profile。准备、启动和停止携带请求标识，并经创建者串行编排；同一标识重查原结果，不重复复制或启动，内容不同则拒绝。停止重入返回原收尾状态；未知终态先查结果，不能重新启动一份代替查询。
- bind 由调用方显式确认，传入接入记录位置及预期 session_id，再验当前 PID、精确路径、心跳和协议；返回本 MCP 进程所绑定的对象与能力。新入口内同一会话只允许一个动作客户端：复用 `sessions.SessionLease` 的进程级文件锁，在控制绑定存续期间持有独立的会话控制锁；第二客户端仍可查询和请求暂停，但获取控制权失败时不得恢复或发送普通动作。该锁不替代逐命令的 host.lock，也不修改桥的 1.5 秒租约或协议。客户端退出由操作系统释放锁；解绑停止自身续租，暂停／释放沿用原桥确认条件，不能因锁释放或桥租约到期便声称目标已松键。旧入口不会自动参加新锁，启动摘要须说明不可同时使用旧客户端直接控制同一桥。
- bind 不自动恢复，也不改变其他 GUI／MCP 进程的活动游戏。已有动作执行中或观察会话未妥善停止时拒绝换绑，不静默暂停另一项任务冒充接管。
- 绑定上下文携带 BridgeClient 的真实目录及运行态 profile，解决现有默认 state/control 与不同后端 bridge 目录不一致；不要求用户填写这些路径。停止、目标退出或身份校验失效后，该上下文明确失效，不悄悄回退至之前的游戏或按进程名寻找替代目标。
- 新绑定期间旧 `click`／`key` 不得转到桌面键鼠；以明确错误引导使用统一 `control_*`，不猜测键码或坐标到引擎动作的映射。旧存档恢复和 `kill_game` 不能借绑定旁路数据与进程所有权规则；无存档初版不开放存档写入，终止须走创建者的 `game_stop`。绑定状态和桥观察必须查询当前受控目标，独立桌面上不可用的窗口观察操作明确报不可用。
- 没有新绑定上下文时，旧 GAMEQAKIT_PROFILE、显式 directory 和既有工具调用继续可用。新上下文不得容许另一个 directory 无提示覆盖其会话目标。`game_unbind` 仅在本客户端动作结束、暂停／释放已确认或目标已退出后清除连接，不终止连接者不拥有的游戏；解绑后进入无活动目标状态，恢复旧 profile 也须显式选择。失效绑定同样保持无目标，不能以旧兼容分支绕过停止后的失效保护。
- 后端协议与线格式不变；若实施中真的需要改 control.py 的协议语义，必须同步旧桥与各自测试，不能借入口功能偷偷改协议。

人工观察继续调用现有 sessions/watch。受控游戏的动作证据继续用原桥截图和回执，不复制图片，也不把会话序号当真实帧。独立桌面的窗口不能由默认桌面观察器假装可直接枚举；后续需观察受控会话时读取既有桥证据，不能为了“共用观察链”绕过桌面约束或启动两个采集器。

## 9. 界面与失败反馈约束

沿用现有 PyQt6、中文字体、配色和图标，不在这一轮重做侧栏或卡片风格，不下载字体和图片。具体界面布局与视觉稿在实施规划前另行展示，不把本文件当已完成的 UI 设计。

必要交互要求：

- 人工观察与 AI 接入明确区分；默认选择、检查或连接都不发游戏输入。
- 列出阻碍及可行下一步，不以单一绿色“支持”徽标掩盖差异；状态必须有文字，不只靠颜色。
- 检查、复制、启动及收尾移到 worker；即时显示正在执行的步骤，不编造百分比或预计耗时。
- 长步骤可取消，重复开始不可重入；关闭和失败有明确结果，不能仍停在“尚未开始”。
- 不强制激活或置顶游戏窗口，不移动系统光标；所有目标进程可见窗口的层级按已验后端处理。
- Tab 顺序、键盘操作、可访问名称、焦点提示、44px 主要点击目标及高 DPI 缩放纳入自动检查；测试小／常规／大窗口宽度。
- 连接保守失败、缺首图、陈旧心跳、暂停未确认、数据校验失败、回收失败必须独立可见；不能统一显示“就绪”或要求用户反复重试。

1. 检查纯只读，未知构建／缺依赖／保存边界不明不复制、不加载、不发输入；有界发现不扫描整盘。
2. 源目录重叠、既有目标、链接、依赖／源 EXE 在确认后变动、同名多实例和陈旧 PID 拒绝。

4. 新入口经真实 MCP 完成连接、显式恢复、正常输入、动作后图、暂停、解绑与创建者停止；验证外部连接者不能停止／回收。受控绑定时旧桌面输入、存档恢复、按名字终止和跨目录动作均不能旁路，目标退出或解绑后无旧目标回退；不以直接调用插件代替入口。
5. 并发 GUI／MCP 操作与重复请求不产生两个副本，单一动作客户端、连接者退出与租约失效均验证，不抢占另一会话，不盲重发未知动作。
6. 原目录、外部数据及保留进度摘要；成功与失败证据可打开，运行副本的数据处置可追踪。
7. 旧 GUI 人工盯屏、原 profile、CLI 和 MCP 行为回归；支持边界不因入口存在而扩大。

## 11. 交付、回退与审阅点

每个独立开发块验证后提交，保留旧人工入口、旧 profile 和适配器命令。公开文档只用通用目录标记，不提交游戏、二进制、本机绝对路径、存档或原始运行证据。

回退先停止新入口创建的会话并检查自有进程退出，再恢复入口／元数据版本；不把新版会话强行交给旧版续跑。旧观察记录无需迁移。收尾不确定时保留副本与证据，不能为获得“干净状态”删掉用户数据。

本设计需要用户审阅的主要选择：

1. 保留现有主程序，增加薄接入层，而非重写控制台或把测试脚本当启动器。
2. 首批交付为通用核心、人工观察／显式连接和固定原生后端的完整生命周期；其余后端按安全启动条件逐个迁入，不宣称全部引擎一键可用。
3. 所有真人体验统一留到最后；中间依靠自动与真实副本验证推进，支持声明继续标清未验范围。

第 3 项已由用户明确决定；前两项是本设计建议。首版的附带边界也需一并审阅：创建者存活期间拥有进程，外部连接者不能代为停止／回收；新入口内单一动作客户端；受控绑定不开放旧桌面键鼠和存档写入旁路。上述约束不改变未绑定旧入口的行为。

批准后再编制实现计划并开始功能编码；具体 UI 布局另行展示，架构批准不等于视觉稿已验收。本次只提交设计与路线同步，不修改认证、目标绑定、启动逻辑或任何游戏数据。
