# 汉化巡检总控

助手做判断和记录，人工手玩与已验证的 AI 控制共用留证。开始巡检不是先写一套新自动化。

## When NOT to use

- 普通功能开发、非游戏项目、只改文案不巡检
- Trellis 任务生命周期（建任务、归档、提交仪式）
- 给已有 QA 工具加功能（那是工具仓库的事）

有 Trellis 时本 Skill 只约束巡检判断，不抢 Trellis 主控。

## 分工

| 谁 | 做什么 |
|---|---|
| 人 | 手玩；标记疑点；最终验收风格/专名 |
| 工具 | 盯屏留证、去重提示、存档快照。换游戏只新建 profile，不改核心 |
| 助手 | 按下面的门判断、落记录、能修的当场修 |

禁止为新游戏重造截图/盯屏/去重引擎。已有跨游戏盯屏工具则换 profile 使用。输入模拟和改档是辅助，默认低优先。

## 工具发现与操作方式

先读取当前 MCP 的真实工具列表与参数，不假定命名空间或引擎能力。识别出引擎不代表已经安装控制插件。

| 当前条件 | 最小流程 |
|---|---|
| 人在手玩 | `watch_start` 启动留证 → `watch_status` 核对采集、积压、丢帧与降级 → `watch_events` 分页复核候选；观察链不发输入 |
| 已授权 AI，且插件状态健康 | `control_status` 核对精确路径/PID、帧、暂停、held 和实际能力 → `control_action` 正常输入；需要看画面时使用工具支持的 `include_image` |
| 动作成功且已返回新帧与截图 | 直接核对本次回执、场景/位置和画面；不再例行调用 `capture` 或 `control_result` 重复获取相同证据 |
| 超时、pending 或结果不明 | 按原 `command_id` 查询 `control_result`；不换编号盲重发。`historical=true` 的旧回执不能指导当前动作 |
| 人工接管 | `control_pause` 仅表示请求；再查 `control_status`，确认 paused 且 held 为空。恢复 AI 需明确授权并使用新的恢复命令 |

Unity 接入先读本仓库 `plugins/unity/README.md` 的版本／后端矩阵，按实际 Mono／IL2CPP 与旧 Input／新 Input System／Rewired 组合使用构建，沿用上述 MCP；发现加载器不等于兼容。商业副本须先核查并记录写入隔离，菜单／剧情通过不代表角色移动或全流程。暂停只接受 connected=true、paused=true、held=[] 的真实确认；同一场景里的菜单变化也必须读图判断。开场／对话可能临时锁定移动，先正常推进到可操作状态，再用位移前后截图与坐标验证，不能只凭回执判通过。未覆盖的设备、API、动态程序集和其他组合另验，不回退桌面输入。

HSP 接入先读 `plugins/hsp/README.md`：当前实证限 Windows x86／官方 HSP 3.7 空白工程与八星帝外置字节码的标题／读取菜单。原内嵌 EXE 不自动加载旁边修改的脚本；先准备已核对保存位置的隔离副本。仍使用上表统一 MCP，按操作后截图核对分页／返回；不把菜单通过扩大为玩法、进度读写或其他版本兼容。

DuckStation／PS1 接入先读 `plugins/duckstation/README.md`，核对完整 EXE 哈希和独立便携副本，原配置／记忆卡／镜像只读。使用上表统一 MCP 与正常虚拟手柄输入；回执按原生执行帧计时，SDL 回调不能当游戏帧。启动固定等待不是就绪检测，必须读回画面；暂停需连接有效、held 为空、原生与 SDL 按钮为零。当前已逐图验证《妖精战士3》开局剧情、屋内移动、记录册保存／读取与重启读测试卡、方块菜单往返，以及桥梁首战的走格、命令、双方回合、伤害／升级与战后离桥返回世界地图（见 `<PS1验证目录>/battle-retest/战斗验证.md`），不能扩大为任意战斗或全流程。菜单用 `control_action(action="press",button="square",frames=12)`，先查 `control_status.buttons`；Start／`shift` 不作为菜单键。动作释放后首图黑场仅在原 3 秒内每 30 原生帧观察，到期仍停止；显式恢复后的画面不追认原失败命令，未知结果先按原编号查询。换盘、音频、实体手柄干扰及其他构建另验。

Wolf RPG 接入先读 `plugins/wolf/README.md`，仅固定 EXE 哈希的官方 Windows x86 范例已有正式桥实证。原目录／保存只读，在新独立桌面副本加载 DLL 与加载器，沿用上表 MCP。回执取完整循环，输入轮询次数不能代替帧；普通动作释放后还有两轮观察。暂停需连接有效、held 为空且 `at_frame_boundary=true` 再核对帧稳定。标题、正常对话、左右位移与菜单往返已有画面证据；移动松键后先走完当前格，菜单退出要等动画完毕。其他构建、商业游戏、存读档和战斗未验；识别 Wolf 不等于已有可用桥，写入守卫不等于完整沙箱，失败不回退桌面输入。

OCR 缺失时继续普通留图并明确降级；窗口标题规则不能代替画面文字检查。自动候选为空不代表无缺陷，YOLO 输出也只作候选。
后台能力缺失、画面失效或状态陈旧时停止 AI 操作，不退回抢前台的 `key` / `click`。通过引擎正常输入测试，不直接改任务结果、跳场景。

## 分类

先看实机画面，再归类。不要凭静态扫描或模型「看了一眼」结案。

| 类 | 标准 | 处理 |
|---|---|---|
| 缺陷 | 界面应中文却仍是原文、乱码、错位对话、功能坏了 | 先截图落盘，再记；乱码等明确错误可当场修 |
| 风格候选 | 专名、双语、是否翻译 OK/菜单英文、措辞口味 | 记候选，交给人判，不擅自改 |
| 非缺陷 | 读源文件的编码乱码、空窗/空报告等已确认设计、重复的已覆盖画面 | 不记缺陷 |

静态文本扫描只能排除「文本层还有没有原文」。扫描通过 ≠ 界面已汉化。图片烘焙、碎字符串、运行时拼出来的 UI，扫描本来就看不见。

## 截图交付与分类

- 对外查看目录默认使用 `问题总览.md`、`已确认/`、`待核实/`；目录只区分确认状态，具体问题类型、场景、复现入口和证据关系由总览说明。两类图片内部平铺，不按编号、地图、日期或来源继续套目录；只建有内容的目录，有用户约定时以约定为准。
- 总览按独立问题列出简短现象、触发位置／步骤摘要、证据状态、问题截图、正常对照和详细记录链接。同一问题的多张图在同一条目关联，读者无需跨目录自行拼接上下文；待核实原因必须明确，翻译疑点不升级为确定缺陷。
- 用户提供的截图与助手发现的截图纳入同一套分类；已有原图保护约定时遵循其边界，用户明确授权一起整理后同步归类。分类不改变问题的证据等级，缺少适用范围、上下文或复现依据的现象仍待核实。
- 中文文件名说明场景及具体现象，裁片、多帧汇总和正常对照标明用途。保留用户原文件名，除非用户明确要求改名；名称包含“重新进入／复现”不等于已有独立复现证据。
- 正常对照保留在内部证据目录，由总览在对应问题旁直接链接，不必在展示目录单设一类，不计缺陷。移除重复展示副本前先确认内部原图存在且SHA-256一致，并按已获授权处理；来源未核清的重复问题图保留并注明，不能用哈希相同的两份图证明两次独立复现。过程截图、日志和内部定位记录留工作区。
- 同图包含不同状态的现象时，按主要已证实问题归档，在总览与详细记录中逐项注明状态并共用原图引用；图中已确认乱码不代表其措辞候选、专名或菜单明暗差异也已确认。无需为每项现象复制同图到多个类别。
- 分开统计截图张数与独立问题数；多图可对应同一问题，单图也可包含多项现象。漏译、显示异常与运行报错分别表述，不能把所有问题图统称为“报错”。
- 整理前盘点文件、证据状态及重复关系，给出具体方案后按授权执行。移动前核对源文件、目标无冲突与内容哈希，整理后逐张核验哈希并同步所有证据引用和项目保护约定，避免原图遗漏或链接失效；不覆盖图片。核对Git忽略规则是否放行两类目录中的图片及总览。对外交付须包含链接依赖的内部证据，或整理为可独立打开的交付包，不能只发送展示目录导致对照与复现链接断开。

## 证据门

没有落盘的实机画面，就不能声称巡检做过或问题已确认。

- 只在状态对不上、新事件/选择/结算/异常时读画面；普通台词和已覆盖的重复结算不要逐页截。
- 优先裁文字区，查看后从模型上下文释放图片；落盘原图按项目留存约定处理，不因已读完而删除。问题图保留在项目测试记录里，之后用路径引用，不要反复把同一张图塞进上下文。
- 工具去重（dHash 等）只提示「这帧不必再看一遍」，不得当作画面未变、分支已走完、或没有错误。
- 「无新增」但没有记录条目和截图 = 没做。

## 字形与编码

- 疑似日文残留必须先把日文和繁体中文的同形/异体字分开。「諜、難、歡」这类繁体字形本身不是日文证据。
- 视觉模型常把繁体「纠正」成日文。候选字形用原图像素核对，不要用模型读出来的字当证据。
- 工具直接读取日文源文件出现的乱码，是编码不匹配，不是游戏内乱码，不得记为缺陷。

## 改档

测试可以改数据减肝。改了必须能还原。共享给汉化或技术的存档必须能区分「原进度档」和「测试减肝档」；未记录的改档不得当原档交付。

记：改了什么、哪个存档/槽、改前备份、还原方法。账本路径由**当前游戏项目**指定，不要抄其他游戏的路径。本条细节见全局规范「测试改档可追溯可还原」。

局部验证用游戏内存档 + 项目外锚点读回，不要为了验证一个分支从头重开。覆盖正在用的存档前先等人批准。

## 推进

- 主会话直接推进。不要靠堆子代理和流程仪式带动游戏进度。
- 人的一句状态陈述是待核验声明。报告和自动化假设冲突时，信人的报告，用新截图核对后再操作。
- 人工盯屏找不到目标窗口时停止，请人确认；不要靠改文件、重启、读档假装推进。已授权的独立桌面插件若身份、心跳与操作后画面均正常，沿其通路操作，不因默认桌面查不到窗口而抢焦点或重启。

## 新游戏第一步

1. 在当前项目写清：测试记录目录、改档账本路径、验收标准。
2. 从运行窗口选择并核对程序路径与当前 PID，生成 profile；同名 `Game.exe` 不靠进程名猜。独立桌面会话按已验证的插件身份绑定。
3. 默认人玩 + 盯屏；明确授权且后台能力实测成立时才由 AI 控制。助手均按本 Skill 判断。
4. 只有工具缺能力、且人明确要求时，才去改工具仓库。
